Category 1: Data Storage Patterns
6 patterns
1
StoragePostgreSQL · MySQL · MongoDB🔥 Nagarro
Primary-Replica (Leader-Follower)
▼

One database server (the primary) handles all writes. One or more replicas receive copies of the writes and handle reads. If the primary fails, a replica is promoted to become the new primary.

When to use: Any system where reads vastly outnumber writes — social media feeds, product catalogs, user profiles. Scale reads horizontally by adding more replicas.
Trade-off: Replicas may lag behind the primary (replication lag) → stale reads. Synchronous replication = zero lag but slower writes. Asynchronous = fast writes but risk of stale data.
Real examples: Instagram reads from replicas, writes to primary. thesqua.re PostgreSQL on Cloud SQL uses read replicas for property search. WordPress, Shopify — all use this pattern.
Read ScalabilityHigh AvailabilityFailover
Cross Questions:
  • What is replication lag and when is it a problem? → Time between write on primary and availability on replica. Problem for: checking if payment went through, reading your own profile after update. Fix: route these reads to primary.
  • How do you handle primary failure (failover)? → Automated: Patroni (PostgreSQL), MHA (MySQL), or cloud-managed (RDS Multi-AZ). Replica with most up-to-date WAL is promoted. DNS updated to point to new primary.
  • Difference between replication and sharding? → Replication = copies of same data for availability + read scaling. Sharding = different data on different servers for write scaling + storage scaling.
  • When would you NOT use replicas? → Financial transactions, inventory checks where stale reads cause real problems. Route those directly to primary.
2
StorageDynamoDB · Cassandra · MySQL🔥 Important
Sharding (Horizontal Partitioning)
▼

Split data across multiple database servers. Each server (shard) holds a portion. A shard key determines which shard holds which data.

Strategies: Hash-based (userId % numShards — even distribution), Range-based (A-M on shard 1, N-Z on shard 2 — enables range queries), Directory-based (lookup table maps key → shard — flexible but lookup bottleneck).

When to use: Single database cannot handle write throughput or storage volume. A user table with 1 billion rows and 100K writes/sec needs sharding.
Trade-off: Cross-shard queries expensive (scatter-gather). Wrong shard key creates hot spots. Resharding is painful — requires data migration and often downtime.
Real examples: Twitter shards tweets by tweet_id. WhatsApp shards messages by chat_id. Instagram shards media by user_id.
Write ScalabilityStorage ScalabilityHorizontal Partitioning
Cross Questions:
  • What is a hot spot and how do you prevent it? → One shard receives disproportionate traffic (e.g., all requests for one celebrity). Fix: add random salt to shard key, use consistent hashing with virtual nodes, or route hot users to dedicated shards.
  • How do you handle cross-shard queries? → Scatter-gather: send query to all shards, merge results. Expensive. Design data model to avoid them — co-locate related data (users + their posts) on the same shard.
  • What is resharding and why is it painful? → Changing number of shards means moving data. With modular hashing, ALL keys remap. With consistent hashing, only ~1/N keys move. Always plan capacity upfront to avoid resharding.
  • Difference between vertical and horizontal partitioning? → Horizontal = sharding (split rows). Vertical = split columns across tables/DBs (user profile DB, user activity DB separately).
3
StorageRedis Cluster · DynamoDB · Cassandra
Consistent Hashing
▼

A hashing scheme where adding or removing a server only requires remapping a small fraction of keys — not all of them. Servers and keys are placed on a virtual ring. Each key maps to the nearest server clockwise.

When to use: Distributed caches (Redis Cluster), distributed databases (DynamoDB, Cassandra), CDN routing. Any system where nodes are added/removed frequently and you want to minimise data movement.
Trade-off: More complex than modular hashing. Can produce uneven distribution without virtual nodes — each physical server maps to multiple positions on the ring (150 virtual nodes is standard).
Key insight: With regular hashing: add 1 server → ALL keys remap. With consistent hashing: add 1 server → only ~1/N keys remap. DynamoDB, Cassandra, and Amazon's Dynamo paper all use this.
Minimal RemappingDistributed CacheVirtual Nodes
Cross Questions:
  • Why use virtual nodes? → Without them, servers are unevenly spaced → uneven load. 150 virtual nodes per physical server ensures statistically even key distribution.
  • How does this handle server failures? → When S2 fails, only S2's keys remap to S3 (next clockwise). All other servers unaffected.
  • How is Cassandra's ring different? → Cassandra uses consistent hashing for partitions. Each node is responsible for a token range on the ring. Replication factor determines how many consecutive nodes also store each key.
4
StoragePostgreSQL WAL · Debezium · Kafka
Write-Ahead Log (WAL)
▼

Before writing data to main storage, write the operation to a sequential append-only log file. On crash, replay the log on restart to recover incomplete operations.

When to use: Every reliable database uses WAL internally (PostgreSQL, MySQL, Cassandra). Also used for: database replication (replicas replay primary's WAL), Change Data Capture (CDC) via Debezium.
Trade-off: Double-write overhead (log + storage). Log grows continuously, needs periodic compaction/truncation (checkpointing).
Cross Questions:
  • What is Change Data Capture (CDC)? → Reading the database's WAL to detect changes (INSERT/UPDATE/DELETE) and stream them to other systems. Standard stack: Debezium → Kafka → downstream consumers. Used to keep search indexes in sync.
  • How does WAL enable replication? → Replicas receive and replay the primary's WAL entries. They arrive at the same state by executing the same operations in the same order.
  • What is log compaction? → Keeping only the latest value for each key, removing intermediate states. Kafka log compaction works this way. Reduces storage while preserving current state.
5
StorageEvent Store · Axon · Kafka
Event Sourcing
▼

Instead of storing current state, store a sequence of events that happened. Current state is derived by replaying events.

When to use: Systems where audit history is critical (financial, compliance). Need to reconstruct past states ("what was user's cart 3 days ago?"). Multiple views of same data needed.
Trade-off: Querying current state requires replaying events (use snapshots every N events). Event schema evolution complex. Storage grows indefinitely.
Audit TrailTemporal QueriesImmutable Log
Cross Questions:
  • What is a snapshot in event sourcing? → Periodic saved state so you don't replay 10,000 events every time. Replay from last snapshot + events since snapshot. Typically snapshot every 50-100 events.
  • How does event sourcing + CQRS work together? → Event sourcing emits events from write side. CQRS projects those events into read-optimised views (denormalized tables, search indexes). Commands → Events → Projections → Queries.
  • When would you NOT use event sourcing? → Simple CRUD where you just need current state. Adds significant complexity. Only worth it when audit trail, temporal queries, or event replay are genuinely needed.
6
StoragePostgreSQL + Elasticsearch
CQRS (Command Query Responsibility Segregation)
▼

Separate the write model (commands: create, update, delete — optimised for consistency) from the read model (queries — optimised for fast reads, may use different DB or schema).

When to use: Systems with very different read and write patterns. E-commerce: write orders to normalised PostgreSQL, but serve product catalog from denormalised Elasticsearch.
Trade-off: Two models to maintain. Synchronisation mechanism between them. Eventual consistency — read model may lag the write model.
Read/Write SeparationEventual ConsistencyQuery Optimisation
Cross Questions:
  • How do you keep the read model in sync? → Event-driven: write model emits events, async consumers update read model. CDC (Debezium) reads WAL and streams to read model. Accept eventual consistency.
  • When does the user see stale data? → Between the time a command executes and the async projection updates. For most cases this lag is milliseconds and acceptable. For critical reads, query write model directly.
  • Does CQRS always require event sourcing? → No. You can implement CQRS with direct DB sync or CDC without event sourcing. They complement each other but neither requires the other.

Category 2: Caching Patterns
5 patterns
7
CachingRedis · Memcached🔥 Default Pattern
Cache-Aside (Lazy Loading)
▼

Application checks cache first. Cache hit → return cached data. Cache miss → load from DB, return data, populate cache for next time.

When to use: Default strategy for most applications. Works well when reads far outnumber writes and cache misses are tolerable. Most flexible — app controls what gets cached.
Trade-off: First request always slow (cold start). Cache and DB can become inconsistent if DB updated without invalidating cache (stale data window).
Lazy LoadingRead OptimisationTTL-based Invalidation
Cross Questions:
  • What is cache invalidation and why is it hard? → Keeping cache and DB in sync when data changes. TTL-based (simple, stale until expiry), event-driven (invalidate on write, complex), write-through (always update both). "There are only 2 hard problems in CS: cache invalidation and naming things."
  • What is a cache stampede (thundering herd)? → Popular cache entry expires → thousands of simultaneous requests hit DB. Fix: mutex lock (one request loads DB, others wait), probabilistic early expiry (randomly refresh before TTL expires), stale-while-revalidate.
  • What is LRU eviction? → Least Recently Used — when cache full, evict item accessed longest ago. Redis supports LRU, LFU (least frequently used), and TTL-based. Choose based on access pattern: LRU for recency bias, LFU for frequency bias.
  • What cache hit ratio is good? → Target 90%+. Below 80% means cache isn't helping much — reconsider what you cache or increase cache size.
8–11
Caching🔥 Know All 4
Write-Through · Write-Behind · Read-Through · Cache Stampede Prevention
▼

Write-Through (P8): Every write goes to cache AND database simultaneously. Cache always up to date. Slower writes (2 writes instead of 1). Wasted space for rarely-read data. Best for: user profiles, settings where read-after-write consistency critical.

Write-Behind / Write-Back (P9): Writes go to cache first, async flush to DB in batches. Fast writes. Risk of data loss if cache crashes. Best for: gaming leaderboards, analytics counters, session stores where brief inconsistency OK.

Read-Through (P10): Cache loads from DB on miss automatically. App only talks to cache, never DB directly. Simplifies app layer. Cache couples to data layer. Best for: when you want caching logic in infrastructure not application code.

Cache Stampede Prevention (P11): When popular entry expires, thousands hit DB simultaneously. Solutions: mutex lock (only first request loads DB, others wait), probabilistic early expiry (randomly refresh before TTL), background refresh.

Decision guide: Default → Cache-Aside. Need write consistency → Write-Through. Need fast writes + can tolerate some loss → Write-Behind. Simplify app code → Read-Through. High traffic + expiring keys → add Stampede Prevention.
Cross Questions:
  • Why is write-behind risky? → If cache server crashes before flushing to DB, you lose the writes. Mitigate with write-ahead log in the cache or use persistent Redis (AOF). Accept the trade-off for performance-critical, loss-tolerant data.
  • What is stale-while-revalidate? → Return stale cached data immediately (fast!), refresh in background. User gets fast response, next user gets fresh data. CDNs (Cloudflare, Fastly) support this natively with Cache-Control headers.
  • How does Redis handle cache invalidation on write? → Cache-aside: on write to DB, call cache.delete(key). Next read will repopulate. Or use write-through: always update cache on write. Or use event-driven: pub/sub message triggers cache invalidation.

Category 3: Communication Patterns
7 patterns (12–18)
12–14
CommunicationREST · BullMQ · Kafka · RabbitMQ🔥 Must Know
Request-Response · Message Queue · Pub/Sub
▼

Request-Response / Synchronous (P12): Client sends request, waits for response. Simplest. REST and gRPC follow this model. Client blocked while waiting. Cascading failures if chain of calls. Use when: immediate answer needed.

Message Queue / Async (P13): Producer puts message on queue. Consumer processes at own pace. Producer doesn't wait. Decouples producer and consumer. Use when: fire-and-forget (send email, process upload, generate report). BullMQ + Redis for Node.js, SQS for AWS.

Publish-Subscribe (P14): Publisher broadcasts to a topic. ALL subscribers receive a copy — unlike queue where each message goes to ONE consumer. Use when: one event, multiple consumers react. "OrderCreated" → inventory service, notification service, analytics service all react simultaneously.

Decision rule: Need immediate answer → Request-Response. Fire and forget / decouple → Queue. One event, multiple consumers → Pub/Sub.
Queue trade-off: Result not immediate. Adds infrastructure. Ordering and exactly-once delivery complex. Pub/Sub trade-off: Subscribers must handle duplicates idempotently. Message ordering across subscribers not guaranteed.
Cross Questions:
  • Queue vs Pub/Sub — when to choose which? → Queue: one message processed by exactly one consumer (task distribution, load balancing workers). Pub/Sub: one event delivered to all subscribers (event fan-out, multiple services reacting to same event).
  • What is exactly-once delivery and why is it hard? → Guarantee message processed exactly once despite failures. Hard because: network can fail after delivery but before ack, and retries cause duplicates. Most systems offer at-least-once. Solution: make consumers idempotent (safe to process same message twice).
  • How does Kafka differ from RabbitMQ? → Kafka: log-based, durable, ordered within partition, consumers pull and can replay. RabbitMQ: traditional message broker, push-based, messages deleted after consumption. Kafka better for event streaming/replay, RabbitMQ better for simple task queues.
15–18
CommunicationKafka · SSE · WebSocket · Webhooks🔥 Frontend-Relevant
Event-Driven · Webhooks · Server-Sent Events · WebSockets
▼

Event-Driven Architecture (P15): Services communicate by emitting and reacting to events. OrderPlaced → inventory reserves stock, payment charges card, notification sends email — all independently, all decoupled.

Webhooks (P16): Server POSTs to client URL when event occurs. "When order ships, POST to https://your-site.com/webhook." Used by: Stripe (payment events), GitHub (push events), Twilio (call events). Client must expose public URL. Delivery not guaranteed — needs retry + idempotency.

Server-Sent Events / SSE (P17): One-directional server→client push over long-lived HTTP. Server sends events as they occur. Client receives without polling. Best for: LLM token streaming, live dashboards, notifications. Simpler than WebSockets.

WebSockets (P18): Bidirectional persistent connection. Both sides send messages anytime. Best for: real-time chat, multiplayer games, collaborative editing. Requires specialized infrastructure for millions of connections.

Decision: Server pushes to browser (one-way) → SSE. Both sides need to send → WebSocket. Third-party integration notification → Webhook. Multiple services react to events → Event-Driven.
Cross Questions:
  • SSE vs WebSocket — when to use each? → SSE: server pushes only (LLM token stream, notifications, live scores). WebSocket: both sides send messages in real-time (chat, multiplayer, collaborative editing, trading terminals).
  • How do you handle webhook delivery failures? → Exponential backoff retry (1m, 5m, 30m, 2h). Store delivery attempts. DLQ for permanently failed deliveries. Idempotency key in webhook payload so clients handle duplicates safely.
  • How does event-driven architecture affect debugging? → Harder — workflow distributed across services and event logs. Use distributed tracing (OpenTelemetry, Jaeger) with correlation IDs flowing through all events. Centralized event log is your audit trail.
  • How does our InterviewAI use SSE? → Streams LLM scoring tokens to frontend as they're generated. Frontend renders typing effect. Token-by-token stream = perceived instant response vs waiting 15 seconds for full response.

Category 4: Reliability Patterns
7 patterns (19–25)
19–25
Reliability🔥 Critical
Circuit Breaker · Retry · Bulkhead · Timeout · Idempotency · DLQ · Graceful Degradation
▼

Circuit Breaker (P19): When downstream service fails repeatedly, stop calling it. Fail fast, return fallback. States: CLOSED (normal) → OPEN (fail fast) → HALF-OPEN (probe recovery) → CLOSED. Prevents cascading failures.

Retry with Exponential Backoff (P20): Retry after 1s, 2s, 4s, 8s. Add jitter (random ±0-1s) to prevent thundering herd on retry storms. Max 3-5 retries. Cloud SDK clients implement this automatically.

Bulkhead (P21): Isolate workloads into separate resource pools. One pool exhausted → others unaffected. Named after watertight ship compartments. Multi-tenant: each tenant has separate thread pool.

Timeout (P22): Maximum duration for every external call. Without timeouts → slow dependency blocks caller indefinitely. Set timeout = 2–3× P99 of healthy response time. Never skip this.

Idempotency (P23): Executing multiple times = same result as once. Client sends idempotency key → server checks for duplicate → returns cached result. Critical for payments, bookings. Implemented in our InterviewAI auth (refresh token) and booking APIs.

Dead Letter Queue / DLQ (P24): Messages that fail after N retries → DLQ for investigation. Without DLQ, one poisonous message blocks all subsequent messages indefinitely.

Graceful Degradation (P25): Non-critical component fails → serve degraded but functional experience. Recommendation service down → show trending. Image slow → text-only. Design failure modes explicitly.

Use together: Timeout → Retry → Circuit Breaker form a hierarchy. Timeout catches slow calls. Retry handles transient failures. Circuit Breaker handles sustained failures (stops retrying to prevent cascade).
Cross Questions:
  • Circuit breaker vs retry — when to use each? → Retry handles transient failures (retry 3x). Circuit breaker handles sustained failures (stop retrying entirely). Use together: retry 3x with backoff → circuit breaker opens after threshold → prevents cascade.
  • What is a cascading failure? → Service A calls B calls C. C fails → B times out → A times out → entire system down. Circuit breaker on each hop prevents this. Bulkhead prevents resource exhaustion spreading.
  • How do you implement idempotency? → Client generates UUID idempotency key. Server: UPSERT with unique constraint on key — if insert fails (duplicate key), return cached response. TTL: 24 hours. In our InterviewAI: refresh token rotation with theft detection is a form of idempotency.
  • Why is timeout the most important reliability pattern? → It's the foundation. Without timeouts, one slow dependency can exhaust all threads, making your service unresponsive. Add timeouts before any other reliability pattern.

Category 5: Scaling Patterns
5 patterns (26–30)
26–30
ScalingNginx · AWS ALB · Cloud SQL · PgBouncer🔥 Must Know
Horizontal Scaling · Vertical Scaling · Load Balancing · Auto-Scaling · DB Connection Pooling
▼

Horizontal Scaling (P26): Add more servers. Requires stateless design — session data in Redis not in-server memory. Load balancer distributes requests. Scales to any size. Use for: web servers, API servers, workers.

Vertical Scaling (P27): Bigger server (more CPU, RAM, disk). Simple — no architecture change. Ceiling exists. Single point of failure. Use for: databases (sharding complex, upgrade hardware simple), quick fixes before going horizontal.

Load Balancing (P28): Algorithms: Round Robin (equal servers), Least Connections (route to least loaded — best for variable request duration), Weighted (powerful servers get more), IP Hash (sticky sessions — same client → same server). L4 (TCP, faster) vs L7 (HTTP, content-aware routing).

Auto-Scaling (P29): Automatically add/remove instances based on metrics (CPU, QPS, queue depth). Scale up takes 2-5 minutes. Scale trigger: CPU > 70% → add instance, CPU < 30% → remove. Cloud: GCP Cloud Run (container-level), AWS Auto Scaling Groups.

DB Connection Pooling (P30): Opening new DB connection = ~50ms + TCP + auth overhead. Maintain pool of reusable connections. Requests borrow, use, return. PgBouncer for PostgreSQL. Too small = wait. Too large = DB overwhelmed. Rule: pool size = (core count × 2) + effective disk spindles.

Key insight: Stateless servers + shared state (Redis/DB) is the foundation of horizontal scaling. If you have state in the server, you can't add more servers safely.
Cross Questions:
  • Why must servers be stateless for horizontal scaling? → If session is in Server 1's memory, next request to Server 2 loses the session. Solution: store all state externally — Redis for sessions, PostgreSQL for persistent data. Any server can then handle any request.
  • L4 vs L7 load balancing? → L4 (transport layer): routes by IP/TCP port. Fast, no content inspection. L7 (application layer): routes by URL path, headers, cookies. Enables content-based routing (/api → API servers, /static → CDN), SSL termination, A/B testing.
  • What is sticky sessions and when is it a problem? → IP hash → same client always hits same server. Problem: if that server goes down, client loses session. Solution: stateless servers + external session store (Redis). Only use sticky sessions when you truly can't externalise state.
  • What metrics trigger auto-scaling? → CPU utilization (traditional), request count/QPS (better for API services), queue depth (best for async workers — scale workers when queue backlog grows).

Category 6: Data Processing Patterns
4 patterns (31–34)
31–34
Data ProcessingHadoop · Flink · Kafka · Debezium
MapReduce · Stream Processing · Lambda Architecture · Change Data Capture (CDC)
▼

MapReduce (P31): Split large dataset across machines (Map phase — each machine processes its portion independently). Combine results (Reduce phase). Foundation of batch processing. Hadoop, Spark. High latency (minutes to hours). Not for real-time.

Stream Processing (P32): Process data as it arrives, event by event, sub-second latency. Kafka Streams, Apache Flink, Spark Streaming. Use for: real-time analytics, fraud detection (flag suspicious transactions instantly), live recommendations.

Lambda Architecture (P33): Run batch AND stream processing in parallel. Batch layer: accurate, high latency (nightly). Stream layer: approximate, low latency (real-time). Serving layer merges both. Analytics showing both real-time trend and daily aggregate.

Change Data Capture / CDC (P34): Capture DB changes (INSERT/UPDATE/DELETE) as event stream. Downstream systems subscribe and react. Debezium reads PostgreSQL WAL → publishes to Kafka → search index, cache, analytics all update in near real-time.

When to use each: Large batch analytics → MapReduce. Real-time dashboards/fraud → Stream Processing. Need both accuracy and real-time → Lambda. Keep search index/cache in sync with DB → CDC.
Lambda Architecture trade-off: Two parallel pipelines = duplicated code, complex maintenance. Kappa Architecture (stream-only, replay for batch) is simpler if stream processing is fast enough for your accuracy needs.
Cross Questions:
  • What is Kappa Architecture? → Simplification of Lambda — only stream processing layer. Replay historical data through stream for batch-level accuracy. Simpler (one pipeline), works when stream processing is fast enough. Preferred when you can afford to trade some complexity for simplicity.
  • How does CDC with Debezium work? → Debezium connects to PostgreSQL as a logical replication slot. Reads WAL in real-time. Publishes each change as a Kafka message. Downstream: Elasticsearch consumer updates search index, Redis consumer invalidates cache. Near real-time sync without polling.
  • What is backpressure in stream processing? → Consumer processes slower than producer produces → buffer fills → memory pressure → crash. Solutions: bounded queues (drop or block on full), adaptive rate limiting, scale consumers automatically when queue grows.

Category 7: API Design Patterns
5 patterns (35–39)
35–39
API DesignKong · AWS API GW · Nginx🔥 Architecture
API Gateway · BFF · Rate Limiting · Cursor Pagination · API Versioning
▼

API Gateway (P35): Single entry point. Handles: auth (validate JWT once, not in every service), rate limiting, routing (/api/v1/users → user service), SSL termination, logging, request transformation. Clients talk to one gateway instead of 20 services. Kong, AWS API Gateway, Nginx.

Backend for Frontend / BFF (P36): Separate API layers per client type. Mobile BFF: lightweight responses, bandwidth-optimised. Web BFF: rich responses, desktop-optimised. Internal tooling BFF: full data access. Use when mobile and web have significantly different data needs.

Rate Limiting (P37): Limit requests per client/IP per time window. Algorithms: Token Bucket (allows bursts, refills at rate R), Fixed Window (simple, boundary spike issue), Sliding Window (accurate, memory intensive). Redis INCR + EXPIRE for distributed rate limiting.

Cursor-Based Pagination (P38): Return opaque cursor pointing to last item. Client passes cursor for next page. Better than offset pagination for large datasets (offset=10000 = scan 10000 rows). Twitter/Facebook timelines use cursor pagination. Downside: can't jump to page 50.

API Versioning (P39): URL versioning (/api/v1/, /api/v2/) most common. Header versioning (Accept: application/vnd.api+json;version=2). Never break existing clients. Maintain old versions for migration window. Deprecation policy: 6 months notice minimum.

Rate limiting algorithms: Token Bucket — best for API rate limiting (allows bursts). Fixed Window — simple but double traffic at window boundary. Sliding Window — most accurate but uses more memory. Leaky Bucket — smooth output, good for API proxies.
Cross Questions:
  • API Gateway vs Reverse Proxy? → Reverse proxy: simpler, handles SSL/routing/load balancing. API Gateway: adds auth, rate limiting, request transformation, API key management, analytics. Nginx = reverse proxy. Kong = API Gateway built on Nginx.
  • Why cursor pagination over offset? → Offset = SELECT * LIMIT 20 OFFSET 10000 → DB scans 10,020 rows, discards 10,000. Cursor = WHERE id > cursor_value LIMIT 20 → uses index, O(1). Also consistent: if items deleted during pagination, offset skips items, cursor doesn't.
  • Token bucket vs sliding window rate limiting? → Token bucket: allows bursting (100 req/10s = can do 100 in 1 second then 0 for 9). Sliding window: 100 req/10s = max 100 in any 10-second window, no bursting. Choose bucket for client experience, window for strict fairness.
  • How does the API Gateway handle microservice discovery? → Service registry (Consul, Kubernetes DNS). Gateway looks up current IPs/ports at request time. No hardcoded backend addresses. Dynamic routing as services scale up/down.

Category 8: Infrastructure Patterns
4 patterns (40–43)
40–43
InfrastructureCloudflare · Nginx · Istio · K8s🔥 Production
CDN · Reverse Proxy · Service Mesh · Sidecar Pattern
▼

CDN (P40): Distribute static content (images, JS, CSS, video) to edge servers worldwide. User in Mumbai served from Mumbai edge, not US origin. Reduces latency from 200ms to 5ms. Cache invalidation delay: new content takes time to propagate. Cloudflare, Akamai, CloudFront.

Reverse Proxy (P41): Sits between clients and backend. Handles: SSL termination (terminate HTTPS at proxy, HTTP internally), compression (gzip), caching, routing, health checks. Nginx, HAProxy, Envoy. Every production web service uses one.

Service Mesh (P42): Infrastructure layer for service-to-service communication. Sidecar proxy (Envoy/Linkerd) alongside each service handles: load balancing, retries, circuit breaking, mutual TLS, distributed tracing, observability. Removes reliability patterns from application code. Use for 50+ microservices.

Sidecar Pattern (P43): Deploy helper process alongside main service in same pod/container group. Sidecar handles cross-cutting concerns: logging (tail log files → ship to Elasticsearch), config (watch for changes → reload main service), monitoring (expose metrics endpoint). Main service stays focused on business logic.

Service Mesh trade-off: Significant operational complexity. Each service gets a sidecar proxy — doubles container count. Debugging becomes harder. Only justified at large scale (50+ services) where implementing reliability patterns in every service is impractical.
Cross Questions:
  • How does CDN cache invalidation work? → URL-based: change URL when content changes (cache-busting with hashes like /app.a3b4c5.js). Cache-Control headers set TTL. Manual purge via Cloudflare/CloudFront API for immediate invalidation.
  • What can you put on a CDN? → Static assets (JS, CSS, images, fonts). Videos. Some CDNs can cache dynamic API responses (edge caching with cache-control headers). Modern CDNs (Cloudflare Workers) can run code at the edge.
  • What is mutual TLS (mTLS) in service mesh? → Both client AND server present certificates. Verifies identity of both parties. Prevents service impersonation within cluster. Service mesh (Istio) handles mTLS transparently without app code changes.
  • How does Cloudflare WAF differ from a reverse proxy? → Both sit in front of your origin. WAF adds security: blocks malicious IPs, SQL injection, XSS, bot protection, DDoS mitigation. We learned this at thesqua.re when Cloudflare WAF blocked Retell AI's webhook IPs.

Category 9: Consistency Patterns
4 patterns (44–47)
44–47
ConsistencyKafka · Zookeeper · etcd🔥 Senior Level
Two-Phase Commit · Saga · Eventual Consistency · Distributed Locking
▼

Two-Phase Commit / 2PC (P44): Atomic transactions across multiple participants. Phase 1: coordinator asks all "can you commit?" Phase 2: if all say yes → commit; any says no → rollback. Problem: if coordinator crashes between phases, participants hold locks indefinitely. Blocking, slow, doesn't scale.

Saga Pattern (P45): Sequence of local transactions. Each service does its transaction, emits event. If step fails → compensating transactions undo previous steps. OrderCreated → PaymentCharged → InventoryReserved. If inventory fails → refund payment → cancel order.

Eventual Consistency (P46): System will eventually reach consistent state given no new updates. Accept temporary inconsistency for availability and performance. DNS propagation is eventually consistent. Social media "likes" count is eventually consistent. CAP theorem: choose CP (consistent+partition tolerant) or AP (available+partition tolerant).

Distributed Locking (P47): Mutex across distributed nodes. Redis SETNX (SET if Not eXists) with TTL. Prevents: double-booking, duplicate payment processing, concurrent cron job execution. Redlock algorithm for high reliability. Zookeeper for stronger guarantees.

Saga vs 2PC: 2PC = synchronous, blocking, single coordinator → single point of failure. Saga = async, non-blocking, each service independently compensates → resilient. Use Saga for microservices. Use 2PC only for same-DB transactions or when you control all participants.
Cross Questions:
  • What problem does Saga solve that 2PC cannot? → 2PC requires all participants to hold locks during the entire transaction. If one is slow or fails, everything blocks. Saga uses local transactions — no distributed locking — and compensating transactions for rollback. Works across microservices with different databases.
  • What is CAP theorem? → Consistency (all nodes see same data), Availability (every request gets response), Partition Tolerance (system works despite network failures). Can only guarantee 2 of 3 when partition occurs. CP: HBase, Zookeeper. AP: Cassandra, DynamoDB (configurable). CA: only in single-node DBs.
  • When is eventual consistency acceptable? → Social media counters (like counts), shopping cart (view is stale, checkout is strongly consistent), DNS, search indexes. Not acceptable: payment processing, inventory checks before booking, auth (checking if token revoked).
  • How does Redis distributed locking work? → SET lock_key "1" NX EX 10 — SET if Not eXists with 10s expiry. If succeeds → you hold lock. On completion → DEL lock_key. Redlock algorithm uses 5 Redis nodes for fault tolerance.

Zero Trust Security (P48): "Never trust, always verify." Every request verified regardless of origin — even from inside the network. No implicit trust based on network location. Verify: identity (JWT/mTLS), device, context. Principles: least privilege access, assume breach, explicit verification.

Distributed Tracing (P49): Track a request as it flows through multiple services. Assign a trace ID at entry. Each service adds a span (start time, duration, metadata). Correlate all spans to reconstruct the full request path. Essential for debugging microservices. OpenTelemetry → Jaeger/Zipkin/Datadog. Langfuse for LLM traces.

Feature Flags (P50): Toggle features at runtime without deployment. Enable for: specific users (beta testers), percentage rollout (10% → 50% → 100%), geographic rollout, A/B testing. Implemented in InterviewAI admin panel. LaunchDarkly, Unleash, or simple DB table. Kill switch for instant rollback.

Feature flags enable: Canary releases (gradually roll out to 5% of users, monitor, expand if healthy). Trunk-based development (merge incomplete features behind flags). A/B testing (compare feature variants with metrics). Instant rollback (flip flag, no deployment needed).
Distributed tracing in practice: User complains "checkout was slow." Without tracing: impossible to know which service was slow. With tracing: trace shows payment service call took 4.8 seconds. Zero to diagnosis in seconds.
Cross Questions:
  • What is a trace vs a span in distributed tracing? → Trace = entire request journey across all services (one trace_id). Span = work done by one service for that request (service name, start time, duration, tags). Multiple spans compose one trace.
  • How do you implement feature flags without a third-party service? → Simple: DB table with key, enabled (boolean), rollout_percentage. Check on each request: SELECT enabled FROM flags WHERE key='new_scoring'. Cache in Redis (1 minute TTL). Update via admin UI. Sufficient for most cases.
  • What is the difference between feature flag, A/B test, and canary release? → Feature flag: binary on/off for a feature. A/B test: compare variant A vs B with statistical measurement. Canary: gradually roll out to % of users to catch bugs before full release. All three use the same flag infrastructure with different intent.
  • Zero Trust in microservices — practical implementation? → mTLS between services (each service has a certificate, verifies the other's). Service accounts with minimal permissions. Every request carries JWT even between internal services. Audit log all inter-service calls. Istio service mesh implements this transparently.

  • Sharding → cross-shard queries
  • Cache → consistency/invalidation
