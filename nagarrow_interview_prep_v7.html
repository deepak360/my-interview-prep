LangChainHot
Why do we need LangChain? What problem does it solve?
▼
Core answer: Building LLM-powered apps requires wiring together many pieces — LLM calls, prompt management, memory, retrieval, tools, output parsing. Without LangChain you write this plumbing from scratch in every project. LangChain is the standard library for this plumbing.

Problems it solves:

  • Prompt management — template variables, versioning, formatting for different models
  • Chaining — output of one LLM call feeds into the next; without LangChain this is manual string passing
  • Retrieval (RAG) — document loading, splitting, embedding, vector search all standardised
  • Tool use — standardised interface to give LLMs the ability to call functions/APIs
  • Memory — conversation history management without manual context window stitching
  • Model switching — swap OpenAI for Anthropic/Gemini with one line change
# Without LangChain — manual plumbing response = openai.chat.completions.create( model="gpt-4o", messages=[{"role":"user","content":prompt}] ) answer = response.choices[0].message.content # With LangChain — composable, swappable from langchain_openai import ChatOpenAI from langchain_core.prompts import ChatPromptTemplate llm = ChatOpenAI(model="gpt-4o") prompt = ChatPromptTemplate.from_template("Answer: {question}") chain = prompt | llm # LCEL pipe operator result = chain.invoke({"question": "What is RAG?"})
Cross questions:
  • Q: When would you NOT use LangChain? → Simple single LLM call with no chaining, retrieval or tools — direct SDK is simpler and has less overhead. LangChain adds abstraction cost.
  • Q: LangChain vs LlamaIndex? → LangChain: general purpose, chains, agents, tools, broad ecosystem. LlamaIndex: specialised for RAG/indexing, better data connectors, more advanced retrieval strategies. Often used together.
  • Q: What is LCEL? → LangChain Expression Language. The pipe operator | composes runnables. Enables streaming, async, batch, tracing out of the box. Replaced the older Chain classes.

What is LCEL (LangChain Expression Language) and how does the Runnable interface work?
▼

LCEL is a declarative way to compose chains using the pipe operator |. Every component implements the Runnable interface, which means every component has the same methods: invoke, stream, batch, ainvoke, astream.

from langchain_core.runnables import RunnablePassthrough, RunnableLambda from langchain_core.output_parsers import StrOutputParser # Every | creates a RunnableSequence chain = prompt | llm | StrOutputParser() # All 4 modes work on any chain chain.invoke({"question": "..."}) # sync await chain.ainvoke({"question": "..."}) # async chain.batch([{"question": "a"}, {"question": "b"}]) # batch for chunk in chain.stream({"question": "..."}): # streaming print(chunk, end="", flush=True) # RunnableParallel — run multiple chains in parallel from langchain_core.runnables import RunnableParallel parallel = RunnableParallel({ "summary": summary_chain, "keywords": keyword_chain, }) result = parallel.invoke({"text": "..."}) # both run in parallel # RunnableLambda — wrap any function as a Runnable upcase = RunnableLambda(lambda x: x.upper()) chain = prompt | llm | StrOutputParser() | upcase
Key insight: Because everything is a Runnable, you can swap components without changing the rest of the chain. Swap ChatOpenAI for ChatAnthropic — everything else stays the same.
Cross questions:
  • Q: What is RunnablePassthrough? → Passes input through unchanged. Used in RAG chains to forward the original question alongside retrieved context. {"context": retriever, "question": RunnablePassthrough()}
  • Q: What is the difference between invoke and stream? → invoke waits for complete response. stream yields tokens as they arrive. Both work identically on any Runnable.
  • Q: How do you add retries to a Runnable? → chain.with_retry(stop_after_attempt=3). Works on any Runnable transparently.

from langchain_core.prompts import ( ChatPromptTemplate, SystemMessagePromptTemplate, HumanMessagePromptTemplate, FewShotChatMessagePromptTemplate ) # Standard chat prompt prompt = ChatPromptTemplate.from_messages([ ("system", "You are a helpful AI. Answer in {language}."), ("human", "{question}"), ]) # Few-shot prompt examples = [ {"input": "happy", "output": "sad"}, {"input": "tall", "output": "short"}, ] example_prompt = ChatPromptTemplate.from_messages([ ("human", "{input}"), ("ai", "{output}") ]) few_shot = FewShotChatMessagePromptTemplate( examples=examples, example_prompt=example_prompt ) final_prompt = ChatPromptTemplate.from_messages([ ("system", "Give the antonym."), few_shot, ("human", "{input}"), ]) # Partial prompts — pre-fill some variables partial = prompt.partial(language="Hindi") chain = partial | llm # only needs {question} now

  • Q: How do you use MessagesPlaceholder for conversation history? → MessagesPlaceholder(variable_name="history") inside from_messages. Pass the list of previous messages as the "history" variable at invoke time.

Structured output in LangChain — with_structured_output vs output parsers
▼
from pydantic import BaseModel, Field from langchain_openai import ChatOpenAI # Method 1: with_structured_output (recommended — uses function calling) class PropertyInfo(BaseModel): city: str = Field(description="City name") price: float = Field(description="Price per night in GBP") available: bool llm = ChatOpenAI(model="gpt-4o") structured_llm = llm.with_structured_output(PropertyInfo) result = structured_llm.invoke("London apartment £180/night, available now") # result.city == "London", result.price == 180.0 # Method 2: JsonOutputParser (parses JSON from LLM text) from langchain_core.output_parsers import JsonOutputParser parser = JsonOutputParser(pydantic_object=PropertyInfo) chain = prompt | llm | parser # Method 3: PydanticOutputParser from langchain_core.output_parsers import PydanticOutputParser parser = PydanticOutputParser(pydantic_object=PropertyInfo) # parser.get_format_instructions() → adds JSON format hint to prompt
Use with_structured_output whenever possible — it uses the model's native function calling to guarantee JSON schema compliance. PydanticOutputParser relies on the model following text instructions, which can fail.
Cross questions:
  • Q: What happens when structured output fails? → with_structured_output raises a ValueError. Wrap in try/except or use .with_retry(). For PydanticOutputParser use OutputFixingParser which re-asks the LLM to fix malformed output.
  • Q: Can you stream structured output? → Yes with JsonOutputParser — it yields partial JSON objects as they stream. with_structured_output waits for the full response before validating Pydantic schema.

Document Loaders and Text Splitters — loading and chunking documents for RAG
▼
from langchain_community.document_loaders import ( PyPDFLoader, WebBaseLoader, CSVLoader, UnstructuredMarkdownLoader ) from langchain_text_splitters import ( RecursiveCharacterTextSplitter, TokenTextSplitter ) # Load documents loader = PyPDFLoader("property_guide.pdf") docs = loader.load() # returns List[Document] # Split into chunks splitter = RecursiveCharacterTextSplitter( chunk_size=1000, # chars per chunk chunk_overlap=200, # overlap prevents context loss at boundaries separators=["\n\n", "\n", ".", " ", ""] ) chunks = splitter.split_documents(docs) # Each chunk: Document(page_content="...", metadata={source, page}) # SemanticTextSplitter — splits on meaning, not size from langchain_experimental.text_splitter import SemanticChunker from langchain_openai import OpenAIEmbeddings semantic_splitter = SemanticChunker(OpenAIEmbeddings())
Why chunk_overlap matters: A sentence about "the rent" might appear at the end of chunk 1. The answer to "what is the rent?" is only found when the question embedding matches a chunk containing that sentence. Overlap ensures boundary sentences appear in at least one chunk.
Cross questions:
  • Q: What chunk size should you use? → Depends on embedding model context window and retrieval task. For OpenAI text-embedding-3: 512-1024 tokens works well. Too small = no context. Too large = dilutes the specific information the query needs.
  • Q: What metadata is preserved on chunks? → Source file path, page number (PDF), URL (web), row number (CSV). You can add custom metadata: Document(page_content=..., metadata={"property_id": "123"})

Vector stores in LangChain — embeddings, similarity search, MMR retrieval
▼
from langchain_openai import OpenAIEmbeddings from langchain_chroma import Chroma from langchain_community.vectorstores import FAISS, Pinecone embeddings = OpenAIEmbeddings(model="text-embedding-3-small") # Create vector store from documents vectorstore = Chroma.from_documents( documents=chunks, embedding=embeddings, persist_directory="./chroma_db" ) # Standard similarity search results = vectorstore.similarity_search("serviced apartments London", k=5) # MMR — Maximal Marginal Relevance (diversity-aware retrieval) results = vectorstore.max_marginal_relevance_search( query="serviced apartments London", k=5, fetch_k=20, lambda_mult=0.5 ) # lambda_mult: 0 = max diversity, 1 = max relevance # As retriever (Runnable interface) retriever = vectorstore.as_retriever( search_type="mmr", search_kwargs={"k": 5, "fetch_k": 20} ) # Full RAG chain from langchain_core.runnables import RunnablePassthrough rag_chain = ( {"context": retriever, "question": RunnablePassthrough()} | prompt | llm | StrOutputParser() )
Cross questions:
  • Q: When to use FAISS vs Chroma vs Pinecone? → FAISS: local, in-memory, fast, no persistence (good for prototyping). Chroma: local with persistence, good for development. Pinecone/Weaviate: production cloud-managed, billions of vectors, metadata filtering.
  • Q: What is hybrid search? → Combine vector similarity (semantic) with BM25 keyword search. Ensemble retriever: EnsembleRetriever(retrievers=[vector_r, bm25_r], weights=[0.7, 0.3]). Better recall than either alone.
  • Q: What is a multi-vector retriever? → Store smaller chunks for retrieval but return the full parent document to the LLM. Better context than retrieving small chunks directly.

Tools and Tool Calling in LangChain — @tool decorator, bind_tools, agent
▼
from langchain_core.tools import tool from langchain_openai import ChatOpenAI # Define tools with @tool decorator @tool def search_properties(city: str, max_price: float) -> str: """Search serviced apartments by city and max price per night.""" # hits your DB / API return f"Found 3 properties in {city} under £{max_price}" @tool def get_weather(city: str) -> str: """Get current weather for a city.""" return f"Weather in {city}: 18°C, cloudy" # Bind tools to LLM llm = ChatOpenAI(model="gpt-4o") llm_with_tools = llm.bind_tools([search_properties, get_weather]) # LLM decides which tool to call response = llm_with_tools.invoke("Find apartments in London under £200") # response.tool_calls → [{"name":"search_properties","args":{"city":"London","max_price":200}}] # Simple agent with create_react_agent from langgraph.prebuilt import create_react_agent agent = create_react_agent( model=llm, tools=[search_properties, get_weather], ) result = agent.invoke({"messages": [{"role":"user","content":"Find me a place in London"}]})
Tool calling flow: LLM sees tool schemas → LLM outputs tool_call (not text) → your code executes the tool → result fed back to LLM → LLM generates final text answer.
Cross questions:
  • Q: What is tool_choice="required"? → Forces the model to always call a tool. llm.bind_tools(tools, tool_choice="required"). Useful when you need structured extraction.
  • Q: How do you handle tool errors? → Wrap tool execution in try/except, return error as a string. The LLM can then decide to retry with different parameters or inform the user.
  • Q: Difference between tool and function in OpenAI terms? → Same concept. OpenAI originally called them "functions", rebranded to "tools". LangChain wraps both. Modern OpenAI API uses tools exclusively.

Memory in LangChain — ConversationBufferMemory vs summary vs token buffer, short vs long term
▼
from langchain_core.chat_history import BaseChatMessageHistory from langchain_community.chat_message_histories import ChatMessageHistory from langchain_core.runnables.history import RunnableWithMessageHistory # In-memory history store (short-term memory) store = {} def get_session_history(session_id: str) -> BaseChatMessageHistory: if session_id not in store: store[session_id] = ChatMessageHistory() return store[session_id] # Wrap chain with history chain_with_history = RunnableWithMessageHistory( chain, get_session_history, input_messages_key="input", history_messages_key="history", ) chain_with_history.invoke( {"input": "What apartments do you have in London?"}, config={"configurable": {"session_id": "user_123"}} ) # Long-term memory — persist across sessions (Redis/DB) from langchain_community.chat_message_histories import RedisChatMessageHistory def get_redis_history(session_id: str): return RedisChatMessageHistory( session_id=session_id, url="redis://localhost:6379" ) # Now history survives server restarts
Short-term memory = in-memory, lost on restart (ChatMessageHistory). Long-term memory = persisted to Redis/DB/file (RedisChatMessageHistory, SQLChatMessageHistory). For production always use long-term. In LangGraph, memory is managed via checkpointers — more powerful.
Cross questions:
  • Q: What is ConversationSummaryMemory? → Instead of storing all messages, summarises old messages periodically. Keeps context window manageable for long conversations. LLM generates the summary itself.
  • Q: Token buffer vs message buffer memory? → Message buffer: keep last N messages. Token buffer: keep last N tokens worth of messages. Token buffer is more precise for context window management.
  • Q: How does memory work in LangGraph vs LangChain? → LangChain: memory added as a wrapper around a chain. LangGraph: memory is first-class — state is persisted via checkpointers, supports multiple conversation threads, time-travel debugging.

▼
from langchain_core.callbacks import StdOutCallbackHandler, BaseCallbackHandler from langchain_core.outputs import LLMResult # Custom callback handler class TokenCountCallback(BaseCallbackHandler): def on_llm_start(self, serialized, prompts, **kwargs): print(f"Calling LLM with {len(prompts[0])} chars") def on_llm_end(self, response: LLMResult, **kwargs): print(f"Tokens used: {response.llm_output}") def on_chain_start(self, serialized, inputs, **kwargs): print(f"Chain started: {serialized['name']}") # Attach callbacks chain = prompt | llm | StrOutputParser() chain.invoke( {"question": "What is RAG?"}, config={"callbacks": [TokenCountCallback(), StdOutCallbackHandler()]} ) # Callbacks fire in order: on_chain_start → on_llm_start → on_llm_end → on_chain_end
Cross questions:
  • Q: What is the difference between LangSmith and callbacks? → Callbacks are synchronous hooks in your code. LangSmith is much richer — visual trace tree, latency, cost, error analysis.
  • Q: What is LANGCHAIN_TRACING_V2? → Environment variable. Set to "true" to auto-send all LangChain runs to LangSmith without any code changes.

Build a complete RAG pipeline — end to end with all components
▼
from langchain_community.document_loaders import WebBaseLoader from langchain_text_splitters import RecursiveCharacterTextSplitter from langchain_openai import OpenAIEmbeddings, ChatOpenAI from langchain_chroma import Chroma from langchain_core.prompts import ChatPromptTemplate from langchain_core.runnables import RunnablePassthrough from langchain_core.output_parsers import StrOutputParser # 1. Load loader = WebBaseLoader("https://thesqua.re/corporate-apartments") docs = loader.load() # 2. Split splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200) chunks = splitter.split_documents(docs) # 3. Embed + Store vectorstore = Chroma.from_documents(chunks, OpenAIEmbeddings()) retriever = vectorstore.as_retriever(search_kwargs={"k": 5}) # 4. Prompt prompt = ChatPromptTemplate.from_messages([ ("system", "Answer based on context only.\n\nContext:\n{context}"), ("human", "{question}") ]) # 5. Chain (LCEL) def format_docs(docs): return "\n\n".join(d.page_content for d in docs) rag_chain = ( {"context": retriever | format_docs, "question": RunnablePassthrough()} | prompt | ChatOpenAI(model="gpt-4o") | StrOutputParser() ) answer = rag_chain.invoke("What types of apartments are available?")
Cross questions:
  • Q: How do you evaluate RAG quality? → Metrics: Context Recall (were relevant docs retrieved?), Faithfulness (is answer grounded in context?), Answer Relevance (does answer address the question?). Tools: RAGAS framework, LangSmith evaluations.
  • Q: What is query transformation? → Rewrite the user query before retrieval to improve recall. Techniques: HyDE (generate hypothetical document, embed that), multi-query (generate 3 variants, combine results), step-back prompting (ask broader question first).

Tricky: What is the difference between a Chain, an Agent, and a Graph in the LangChain ecosystem?
▼
ConceptControl flowWhen to use
Chain (LCEL)Deterministic — steps always execute in the same order you definedYou know the exact steps upfront. RAG pipeline, summarisation, translation.
AgentLLM decides — the model chooses which tool to call next based on contextOpen-ended tasks where the number of tool calls is unknown. Research, coding assistant.
Graph (LangGraph)You define nodes and edges — LLM can be at decision nodes but humans can also beComplex multi-step workflows, human-in-the-loop, parallel execution, stateful agents.
Mental model: Chain = recipe (fixed steps). Agent = chef (improvises). Graph = kitchen workflow (stations, roles, human approval required for some steps).
Cross questions:
  • Q: Why did LangGraph replace AgentExecutor? → AgentExecutor had no native support for: human-in-the-loop pauses, streaming intermediate steps, parallel node execution, complex branching, subgraphs. LangGraph provides all of these as first-class features.
  • Q: Can a chain include an agent? → Yes. An agent (LangGraph graph) is a Runnable and can be composed in a chain using LCEL.

LangChainTricky
Scenario: RAG pipeline returns wrong answers. How do you debug it?
▼

Systematic debugging approach:

  • Step 1 — Isolate retrieval: retriever.invoke("query") directly. Are the right documents being retrieved? Wrong chunk size? Missing metadata filter?
  • Step 2 — Inspect context: Print the formatted context being sent to the LLM. Is it readable? Is relevant info present?
  • Step 3 — Test LLM in isolation: Feed the correct context + question directly to the LLM. Does it answer correctly? If yes, retrieval is the problem. If no, prompt is the problem.
  • Step 4 — Check embeddings: Are you using the same embedding model for indexing and querying? Mismatch causes poor retrieval.
  • Step 5 — LangSmith trace: Each step visible with inputs/outputs. Shows exact prompt sent, exact context retrieved, token usage.
# Debug retrieval in isolation docs = retriever.invoke("What is the cancellation policy?") for d in docs: print(f"Source: {d.metadata['source']}") print(f"Content: {d.page_content[:200]}\n")
Q: What are common RAG failure modes? → (1) Retrieval miss — relevant doc not indexed or query doesn't semantically match chunk. Fix: better chunking, query expansion. (2) Context too noisy — 5 retrieved docs dilute the 1 relevant one. Fix: reranking with a cross-encoder. (3) Hallucination despite correct context — prompt doesn't constrain the LLM to use context only. Fix: explicit "answer only from context, say I don't know otherwise" instruction.

LangChainTricky
Tricky: What is the difference between .invoke(), .run(), and .predict() — why are old methods deprecated?
▼
Common trap in interviews: .run() and .predict() were old LangChain v0.1 APIs on Chain objects. They are deprecated in v0.2+. Always use .invoke(), .stream(), .batch() from the Runnable interface.
# OLD (v0.1) — deprecated # chain.run("question here") ← deprecated # llm.predict("question") ← deprecated # NEW (v0.2+) — always use invoke chain.invoke({"question": "question here"}) llm.invoke("question") # Why the change? invoke() returns the correct type # llm.invoke() → AIMessage (not just string) # chain.invoke() → full output dict or parsed output # run() always returned a string — lost type information

The unification of all components under the Runnable interface in LCEL meant all old specific methods (run, predict, apply) were replaced with the universal invoke/stream/batch/ainvoke/astream/abatch pattern.

LangChain with different LLM providers — model switching, fallbacks
▼
from langchain_openai import ChatOpenAI from langchain_anthropic import ChatAnthropic from langchain_google_genai import ChatGoogleGenerativeAI from langchain_ollama import ChatOllama # local models # All use identical interface gpt = ChatOpenAI(model="gpt-4o") claude = ChatAnthropic(model="claude-sonnet-4-6") gemini = ChatGoogleGenerativeAI(model="gemini-2.0-flash") llama = ChatOllama(model="llama3.2") # Jarvis local model # Automatic fallback — try GPT-4, fall back to Claude on failure llm_with_fallback = gpt.with_fallbacks([claude, gemini]) chain = prompt | llm_with_fallback | StrOutputParser() # If GPT-4 rate limits or errors → automatically tries Claude → then Gemini

LangChainTricky
Tricky: Logical question — if every component is a Runnable, what does that mean for testing?
▼

The Runnable interface enables clean unit testing of individual chain components by injecting mock runnables:

from langchain_core.runnables import RunnableLambda # Replace real LLM with mock for testing mock_llm = RunnableLambda(lambda x: AIMessage(content="mocked response")) mock_retriever = RunnableLambda(lambda x: [ Document(page_content="test context") ]) # Test chain with mocks — no API calls, no cost test_chain = ( {"context": mock_retriever | format_docs, "question": RunnablePassthrough()} | prompt | mock_llm | StrOutputParser() ) result = test_chain.invoke("test question") assert result == "mocked response"
Key insight: Because every component implements the same interface, mocking is trivial. RunnableLambda wraps any function as a Runnable. This is the Liskov Substitution Principle (SOLID) in action.

LangGraphHot
Why LangGraph? What does it add over LangChain chains and AgentExecutor?
▼
One-line answer: LangGraph lets you build stateful, multi-step, cyclic workflows for LLM agents — with human-in-the-loop, persistence, and streaming — that chains and AgentExecutor cannot express.
FeatureLangChain chainsAgentExecutorLangGraph
Cycles/loopsNoYes (but opaque)Yes (explicit edges)
Human-in-the-loopNoNoYes (interrupt)
Persistent stateNoNoYes (checkpointers)
Parallel nodesPartial (RunnableParallel)NoYes (fan-out/fan-in)
Time travelNoNoYes (replay from checkpoint)
SubgraphsNoNoYes (nested graphs)
Cross questions:
  • Q: Is LangGraph a replacement for LangChain? → No. LangGraph uses LangChain components (LLMs, prompts, tools, retrievers) inside graph nodes. It's the orchestration layer ON TOP of LangChain, not a replacement.
  • Q: When would you NOT use LangGraph? → Simple linear RAG pipeline, single-turn Q&A, anything that doesn't need cycles or state. Overhead of graph definition isn't worth it for simple chains.

from langgraph.graph import StateGraph, START, END from typing import TypedDict, Annotated from langgraph.graph.message import add_messages # 1. Define the state schema class AgentState(TypedDict): messages: Annotated[list, add_messages] # add_messages reducer appends context: str final_answer: str # 2. Define nodes (functions that transform state) def retrieve_node(state: AgentState) -> dict: question = state["messages"][-1].content docs = retriever.invoke(question) return {"context": "\n".join(d.page_content for d in docs)} def generate_node(state: AgentState) -> dict: answer = llm.invoke(prompt.format( context=state["context"], question=state["messages"][-1].content )) return {"messages": [answer], "final_answer": answer.content} # 3. Build the graph graph = StateGraph(AgentState) graph.add_node("retrieve", retrieve_node) graph.add_node("generate", generate_node) graph.add_edge(START, "retrieve") graph.add_edge("retrieve", "generate") graph.add_edge("generate", END) # 4. Compile and run app = graph.compile() result = app.invoke({"messages": [{"role":"user","content":"What is RAG?"}]})
State is the key concept: Each node receives the FULL current state and returns a dict of state updates. The graph merges updates using reducers. add_messages reducer appends to the list instead of replacing it.
Cross questions:
  • Q: What is a reducer in LangGraph? → A function that determines how a state field is updated. Default reducer = replace. add_messages reducer = append. You can write custom reducers: e.g., always keep the MAX of two values.
  • Q: What is the difference between Annotated and a plain type hint in state? → messages: list = replace messages on update. messages: Annotated[list, add_messages] = append new messages to existing list. Wrong choice of reducer = lost messages or growing memory bloat.

▼
from langgraph.graph import StateGraph, START, END from langchain_core.messages import AIMessage class AgentState(TypedDict): messages: Annotated[list, add_messages] # Decision function — returns node name to go to next def should_continue(state: AgentState) -> str: last = state["messages"][-1] if isinstance(last, AIMessage) and last.tool_calls: return "tools" # LLM wants to call a tool return "end" # LLM gave final answer def call_model(state): return {"messages": [llm_with_tools.invoke(state["messages"])]} def call_tools(state): from langgraph.prebuilt import ToolNode return ToolNode(tools).invoke(state) # ReAct agent loop: model → (maybe tools) → model → (maybe tools) → end graph = StateGraph(AgentState) graph.add_node("agent", call_model) graph.add_node("tools", call_tools) graph.add_edge(START, "agent") # Conditional edge — routing function decides next node graph.add_conditional_edges( "agent", # from this node should_continue, # call this function {"tools": "tools", "end": END} # map return value to next node ) graph.add_edge("tools", "agent") # loop back after tool execution agent = graph.compile()
Cross questions:
  • Q: What is a ReAct agent? → Reason + Act. LLM reasons about the problem, then Acts by calling tools, observes results, reasons again. The loop in the graph IS the ReAct pattern. LangGraph makes this loop explicit and controllable.
  • Q: Can conditional edges return multiple destinations? → Yes — for parallel fan-out. Return a list: return ["node_a", "node_b"]. Both nodes execute in parallel.

Cross questions:
  • Q: What is the difference between short-term and long-term memory in LangGraph? → Short-term: messages in the current thread's state (context window). Long-term: information stored in a separate store (user preferences, facts learned across sessions) retrieved using semantic search. Short-term = within a conversation. Long-term = across conversations.
  • Q: What is a checkpoint vs a state? → State = the current values of all state fields. Checkpoint = a saved snapshot of state at a specific point in the graph execution, with metadata (timestamp, which node was active). Multiple checkpoints per thread = history of the conversation.

▼
# Get full history of a thread history = list(app.get_state_history(config)) # history[0] = most recent, history[-1] = first message # Each entry has: values, metadata, config, next, parent_config for state in history[:3]: print(f"Step: {state.metadata.get('step')}") print(f"Node: {state.metadata.get('writes')}") print(f"Last message: {state.values['messages'][-1].content}") # Replay from a specific checkpoint past_state = history[3] # go back 3 steps # Replay forward from that point result = app.invoke(None, config=past_state.config) # Fork — modify past state and run forward (A/B testing prompts) forked_config = app.update_state( past_state.config, {"messages": [("human", "What about Manchester instead?")]} ) result = app.invoke(None, config=forked_config)

Time travel = literally restoring the exact graph state at a past checkpoint — including all intermediate data, not just messages. Can re-run from the middle of a complex agent workflow, not just from the start.

Cross questions:
  • Q: What is the difference between interrupt_before and interrupt_after? → interrupt_before: pause before the node runs (let human approve/modify the inputs). interrupt_after: pause after the node runs (let human review/edit the outputs before continuing).
  • Q: How do you implement a feedback loop where a human corrects the agent? → Use update_state to inject corrected data, then invoke(None) to continue from that corrected state. The agent never "knew" it was wrong — it just sees correct state going forward.

LangGraphTricky
Scenario: Agent keeps calling the same tool in a loop. How do you fix it?
▼
  • Add a recursion limit: app.invoke(inputs, config, recursion_limit=10) — raises GraphRecursionError after 10 node visits. Prevents infinite loops.
  • Track tool call counts in state: Add tool_call_count: int to state. Increment in tools node. If count > threshold, route to END instead of back to agent.
  • Pass tool results back clearly: Ensure tool outputs clearly say when there's nothing more to do. "No results found. Please try a different search." The LLM should stop calling after seeing this.
  • System prompt instruction: Add "If you receive an error or empty result twice, stop and tell the user what you found so far."
def should_continue(state: AgentState) -> str: # Stop if too many tool calls tool_calls = sum(1 for m in state["messages"] if hasattr(m, "tool_calls") and m.tool_calls) if tool_calls >= 5: return "end" last = state["messages"][-1] if hasattr(last, "tool_calls") and last.tool_calls: return "tools" return "end"

Tricky: What happens when two parallel nodes both update the same state field?
▼
This causes an InvalidUpdateError if you use the default (replace) reducer.

When two parallel nodes return updates to the same field, LangGraph needs to know how to merge them. Without a reducer, it doesn't know which value to use.

from typing import Annotated import operator # Problem: both parallel_node_a and parallel_node_b update "results" # Solution: use a reducer that merges both class ParallelState(TypedDict): query: str # add_messages appends — safe for parallel updates results: Annotated[list, operator.add] # operator.add concatenates lists def web_search(state): return {"results": ["web result 1"]} def db_search(state): return {"results": ["db result 1"]} # After both run: state["results"] == ["web result 1", "db result 1"]

LangSmithTricky
Tricky: How do you use LangSmith to reduce LLM costs in production?
▼
  • Identify expensive runs: Filter LangSmith traces by token count. Find which chains use the most tokens. Often 80% of cost comes from 20% of chains.
  • Trim prompts: LangSmith shows the exact prompt sent. Find bloated system prompts, redundant instructions, unnecessary context.
  • Evaluate smaller models: Use LangSmith datasets + evaluations to compare GPT-4o vs GPT-4o-mini vs Claude Haiku on quality. If quality is equivalent → switch to cheaper model.
  • Cache common queries: LangSmith shows which questions are asked repeatedly. Cache exact-match queries in Redis. Many enterprise chatbots have 30-40% repeated queries.
  • Reduce k in retrievers: If 5 retrieved docs works as well as 10 → half the context → half the tokens for that portion.
Real example: LangSmith trace showed our RAG system was including 3000 token system prompts on every call. Rewrote with 300 tokens. 90% reduction in system prompt cost with no quality loss.

▼

  • Step 2 — Check prompt versions: Prompt Hub shows which prompt version was active at each time. If prompt changed → replay old runs with old prompt vs new prompt.

▼
LibraryLayerWhat it doesYou use it for
LangChainComponentsLLMs, prompts, RAG, tools, parsers, memory — building blocksBuilding individual AI features
LangGraphOrchestrationStateful workflows, cycles, human-in-loop, persistence, subgraphsComplex multi-step agents
LangSmithObservability (cloud)Tracing, evaluation, prompt versioning, monitoring — hostedDebug, evaluate, improve production
LangFuseObservability (OSS)Same as LangSmith but open-source, self-hostable, framework-agnosticSame, but with full data control
How they work together:
1. You build components with LangChain (RAG chain, tools, prompts)
2. You orchestrate them with LangGraph (graph with nodes, edges, state, memory)
3. You monitor and evaluate with LangSmith OR LangFuse (tracing, eval datasets, prompt versioning)

Stack for thesqua.re AI: LangChain (RAG) + LangGraph (booking agent) + LangFuse (self-hosted observability)
