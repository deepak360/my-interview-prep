Performance vs Scalability · Latency vs Throughput
▼
Plain English First
Performance problem: Your website is slow for ONE user. Like one pizza — it takes 30 minutes to bake. That's a performance problem.

Scalability problem: Your website is fast for 10 users but falls apart with 10,000. Like trying to serve 1,000 customers from one pizza oven — you need MORE ovens, not a faster one.

Performance vs Scalability: A service is scalable if it results in increased performance proportional to resources added. If performance increases linearly when you double the servers — great scalability. If adding 100 servers only helps 20% — poor scalability.

Latency vs Throughput analogy
A highway has 4 lanes (throughput) and a 100 km/h speed limit (latency). You can increase throughput by adding lanes. You can decrease latency by increasing speed. They are different things.

Latency: Time to complete ONE operation. "How long does one request take?" Aim for the lowest latency with acceptable throughput.

Throughput: Number of operations per unit time. "How many requests can we handle per second?"

Rule of thumb: Aim for maximum throughput with acceptable latency. A 10ms response time handling 50,000 req/sec is better than a 1ms response time handling 5,000 req/sec for most systems.
Cross Questions:
  • If I have a performance problem, does horizontal scaling help? → No. Horizontal scaling helps with scalability (capacity), not performance of individual requests. Fix performance with better algorithms, caching, faster queries.
  • What is the difference between response time and latency? → Response time = what the client sees (latency + processing + queuing). Latency = network travel time only.
  • What is P99 latency? → 99th percentile. If P99 = 200ms, then 99% of requests finish in under 200ms. The 1% slowest requests take longer. Monitor P99, not average — average hides the pain felt by real users.

CAP Theorem — The most important concept in distributed systems
▼
Plain English Analogy
You have two bank branches in Mumbai and Delhi. When the internet between them breaks (partition):

Option A (CP): Reject all transactions until connection is restored. Your balance is always correct. But the bank is unusable.
Option B (AP): Allow transactions on both sides. The bank stays open. But both branches might not know about each other's recent transactions — temporary inconsistency.

CAP says a distributed system can only guarantee 2 of these 3 things when a network partition occurs:

  • Consistency (C): Every read gets the most recent write or an error. All nodes see the same data at the same time.
  • Availability (A): Every request gets a response (not necessarily the most recent data). No timeouts.
  • Partition Tolerance (P): System keeps working even when network fails between nodes. (In real distributed systems, partition tolerance is REQUIRED — networks do fail. So you're really choosing between C and A.)
Real choices:
CP (Consistent + Partition Tolerant): HBase, Zookeeper, MongoDB (configured). Returns error instead of stale data. Good for: banking, inventory, anything where wrong data is worse than no data.

AP (Available + Partition Tolerant): Cassandra, CouchDB, DynamoDB (default). Returns possible-stale data. Good for: social media, recommendations, anything where availability matters more than perfect consistency.
Consistency patterns:
Weak consistency: After write, reads may not see it. Memcached. Best for: live gaming, video calls (VoIP).
Eventual consistency: After write, reads will eventually see it. DNS, email, social media likes. Most distributed DBs.
Strong consistency: After write, all reads see it. Single-node DBs, RDBMS with transactions. File systems.
Cross Questions — CAP is in every senior interview:
  • Is PostgreSQL CP or AP? → CP when used in a cluster. Single-node PostgreSQL: CA (no partition). In practice for most apps: treat it as strongly consistent (CP).
  • Is Cassandra CP or AP? → AP by default. You can configure read/write quorum to get strong consistency (CP behavior) but you sacrifice availability.
  • What is PACELC? → Extension of CAP for when there IS no partition: also choose between Latency (L) vs Consistency (C). Even in normal operation, replication takes time. DynamoDB = AP/EL (prefers availability, low latency).
  • If someone says "we need 100% uptime AND 100% consistency" — what do you say? → Impossible in a distributed system. CAP theorem guarantees you cannot have both when partitions occur. Design around one or the other.

  • Why is caching the most impactful performance optimization? → RAM access = 100ns, DB query = 1-10ms. Cache hit is 10,000× faster than going to disk. Even a 90% cache hit rate eliminates 90% of slow DB calls.
  • How do you calculate availability when services are chained (in series)? → Multiply: service A (99.9%) calling service B (99.9%) = 99.9% × 99.9% = 99.8%. Chained calls reduce availability. This is why fewer dependencies = better availability.
  • What does achieving 5 nines require? → Redundancy at every level (multiple data centers, no single points of failure), automated failover, chaos engineering to test failure modes, on-call monitoring 24/7. Extremely expensive to maintain.

DNS — How domain names become IP addresses
▼
Plain English Analogy
DNS is like a phone book. You know someone's name (google.com) but need their phone number (IP address: 142.250.80.46) to actually call them. Your phone (browser) asks the phone book (DNS server) to look it up.

DNS translates domain names to IP addresses. Without DNS, you'd type 142.250.80.46 instead of google.com.

How it works:

  • Step 1: Browser checks its local cache. Already visited google.com? Use cached IP.
  • Step 2: Ask OS (which checks hosts file and OS cache).
  • Step 3: Ask your ISP's DNS resolver (recursive resolver).
  • Step 4: Resolver asks Root nameserver → "who handles .com?" → TLD nameserver.
  • Step 5: TLD says "google.com is managed by ns1.google.com" → Authoritative nameserver.
  • Step 6: Authoritative nameserver returns the IP. Cached with TTL.
DNS for load distribution: Round robin DNS — one domain returns multiple IPs, rotated. Geographic DNS — return different IPs based on user's location (CDN routing). Weighted DNS — send 90% traffic to new server, 10% to old (canary deploy).
Trade-off: DNS propagation takes time (TTL, typically minutes to 48 hours). If you change your server IP, old IP may be cached in DNS servers worldwide. Plan deployments accordingly — lower TTL before a planned migration.
Cross Questions:
  • What is TTL in DNS? → Time To Live — how long DNS servers cache the result before re-querying. Low TTL (60s) = fast propagation but more DNS load. High TTL (86400s = 1 day) = less load but slow changes.
  • How does geographic DNS routing work? → DNS server checks your IP's geographic location and returns the IP of the nearest server. This is how CDNs and global services route users to the closest datacenter.
  • What is split-horizon DNS? → Return different IPs for the same domain based on whether query comes from inside or outside the company network. Internal users get internal IP (direct), external get public IP (load balancer).

TCP vs UDP · REST vs RPC — Communication Protocols
▼
TCP vs UDP Analogy
TCP = registered mail. You know it arrived. You get a confirmation. Slower. Guaranteed delivery.
UDP = shouting in a crowded room. Fast. No guarantee everyone heard. Good enough for most real-time situations.

TCP (Transmission Control Protocol): Establishes connection (3-way handshake: SYN → SYN-ACK → ACK). Guarantees delivery and ordering. Retransmits lost packets. Slower. Used for: HTTP/HTTPS, email, file transfer — anywhere correct data matters.

UDP (User Datagram Protocol): No connection. Sends packets, doesn't care if received. Faster (no handshake overhead). Used for: video streaming, VoIP, gaming, DNS — anywhere speed matters more than perfection. Dropped packet = slightly glitchy video, acceptable.

REST vs RPC:
REST: Resource-based. URLs are nouns (/users/123). HTTP verbs (GET, POST, PUT, DELETE). Stateless. Easy to understand. Used for public APIs. Slower (JSON over HTTP/1.1).

RPC (gRPC): Action-based. URLs are verbs (GetUser, CreateOrder). Binary protocol (Protocol Buffers — 5-10× smaller than JSON). HTTP/2 (multiplexing, streaming). Used for internal microservice communication. 7× faster than REST.

When to choose: Public API consumed by web/mobile → REST. Internal service-to-service → gRPC. Need streaming in both directions → gRPC streaming.
Cross Questions:
  • Why is UDP used for video calls if it can lose packets? → Human perception can tolerate a dropped frame or glitchy audio for 10ms. But if we wait for TCP retransmission, we might wait 100ms+ — causing noticeable freeze. Slight degradation is better than freeze.
  • What is the TCP 3-way handshake? → SYN (client: "can we connect?") → SYN-ACK (server: "yes") → ACK (client: "great"). Adds ~1 round-trip latency before any data. HTTP/2 reuses connections (multiplexing) to avoid this overhead per request.
  • What is QUIC? → Google's protocol built on UDP with reliability features of TCP. HTTP/3 uses QUIC. Faster connection establishment (0-RTT reconnect), better than TCP on lossy networks. Used by Cloudflare, Google.

SQL vs NoSQL — When to use which database
▼
Plain English Analogy
SQL = a very organised filing cabinet with labelled folders, strict rules about what goes where, and cross-referencing between folders. Great for complex relationships. Painful to add new folder types.

NoSQL = a pile of documents. Each document can have different fields. Fast to throw in, fast to retrieve. Not great for "show me all documents where the sub-sub-field equals X."

SQL (Relational): Data in tables with rows and columns. Relationships between tables via foreign keys. ACID transactions. Schema enforced. Examples: PostgreSQL, MySQL, SQLite.

NoSQL (Non-Relational): 4 types — Key-Value (Redis, DynamoDB), Document (MongoDB, CouchDB), Wide Column (Cassandra, HBase), Graph (Neo4j).

Choose SQL when: Complex queries and relationships (JOIN across tables). ACID transactions critical (payments, bookings, inventory). Schema is stable and well-defined. Reporting and analytics needed. Team knows SQL well. Default choice for most apps.
Choose NoSQL when: Need to scale to massive write throughput (10M+ writes/sec — Cassandra). Data is hierarchical/document-like (product catalogs with variable fields — MongoDB). Key-value lookups with microsecond latency (Redis). Relationships are graph-like (social networks — Neo4j). Schema needs to change frequently.
Cross Questions — this comes up in every interview:
  • thesqua.re uses PostgreSQL — could you use MongoDB instead? → PostgreSQL is the right choice. Property listings have complex relationships (properties → availability → pricing → bookings → users). SQL JOINs handle this naturally. MongoDB would require application-level joins — more complex, slower. Use MongoDB if property listings had highly variable, unpredictable schemas (they don't).
  • What is denormalization and when do you use it? → Store redundant data to avoid expensive JOINs. Instead of joining users + posts + comments, store user_name directly in each post. Faster reads, slower writes, larger storage. Use when read performance is critical and write performance is acceptable.
  • What is SQL tuning? → Indexes (B-tree on frequently queried columns), avoid SELECT * (only select needed columns), analyze slow queries with EXPLAIN ANALYZE, connection pooling (PgBouncer), query caching, proper indexing on JOIN columns.
  • What is federation (functional partitioning)? → Split one big database into multiple databases by feature. Users DB, Products DB, Orders DB — each deployed separately. Reduces single-DB load. Downside: cross-database queries are hard. Use when different features have very different scale requirements.
S2
Storage Pattern🔥 Nagarro Asked
Primary-Replica · Sharding · Consistent Hashing — Scaling your database
▼
Database Scaling Analogy
Primary-Replica = one head chef (primary) cooks everything, assistants (replicas) serve dishes and handle orders — but only the head chef updates the menu.

Sharding = split the restaurant into 3 sections. Section A handles customers A-M, B handles N-T, C handles U-Z. Each section is independent.

Consistent Hashing = a circular seating arrangement. When a new server joins, only nearby customers are moved — not everyone.

Primary-Replica: Primary handles writes. Replicas copy data and handle reads. Reads outnumber writes in most systems (10:1 ratio typical). Add replicas to scale read capacity without changing write path.

Sharding: Split data across multiple servers. Hash-based (user_id % 3), Range-based (A-M/N-Z), Directory-based (lookup table). Choose shard key carefully — it's hard to change later.

Consistent Hashing: Servers placed on a virtual ring. Add/remove server → only keys near that position remap (1/N keys), not all keys. Solves the "add a server = reshuffle everything" problem of modular hashing. Used by Redis Cluster, Cassandra, DynamoDB.

Sharding trade-offs: Cross-shard queries = expensive scatter-gather. Hot spots if shard key is poorly chosen (celebrity user gets all traffic on one shard). Resharding = painful migration. Plan shard capacity 2-3× upfront.
Read ScalabilityWrite ScalabilityMinimal RemappingHorizontal Partitioning
Cross Questions:
  • When would you choose sharding over read replicas? → Replicas solve read scaling but writes still bottleneck on one primary. When writes exceed single-DB capacity (millions/sec) → shard. For most apps, replicas + vertical scaling is enough before sharding is needed.
  • What are virtual nodes in consistent hashing? → Each physical server is represented by 150 positions on the ring. This ensures even distribution even when servers have different capacities. Cassandra uses 256 virtual nodes per physical node by default.
  • What is master-master replication? → Both nodes can accept writes and replicate to each other. Handles write failures on either node. Downside: write conflicts when both nodes update the same row simultaneously. Requires conflict resolution strategy.
S3
Storage Pattern
Write-Ahead Log · Event Sourcing · CQRS — Advanced storage patterns
▼
WAL Analogy
Write-Ahead Log = a surgeon writing down every step before doing it ("I'm about to cut here, then stitch there..."). If the surgeon collapses mid-operation, a colleague can read the notes and finish/undo the procedure.

WAL: Before writing to main storage, write the operation to an append-only log. On crash, replay the log. PostgreSQL, MySQL, Cassandra all use WAL internally. Also the basis for database replication (replicas replay primary's WAL) and CDC (Debezium reads WAL → Kafka).

Event Sourcing Analogy
Your bank doesn't store "balance: £5000". It stores every transaction: deposited £3000, withdrew £500, deposited £2500... Your current balance is calculated by replaying all transactions. Event sourcing does the same for any data.

Event Sourcing: Store sequence of events instead of current state. OrderCreated → ItemAdded → PaymentReceived → OrderShipped. Replay to get current state. Snapshots every N events for performance.

CQRS (Command Query Responsibility Segregation): Separate write path (optimised for consistency — normalised DB) from read path (optimised for speed — denormalised read model). Write service handles CUD, separate read service handles queries. Sync via events.

When NOT to use Event Sourcing: Simple CRUD apps. Adds enormous complexity. Only worth it when audit history, time-travel queries, or event replay are genuinely core requirements (fintech, compliance, analytics).
Cross Questions:
  • How does WAL enable CDC? → Debezium connects as a PostgreSQL logical replication client. Reads WAL in real-time. Publishes each change (INSERT/UPDATE/DELETE) as a Kafka message. Downstream consumers keep search indexes and caches in sync — without polling.
  • CQRS without event sourcing — is that possible? → Yes. Use CDC (Debezium reads WAL) to sync write DB to read model. No event sourcing needed. CQRS and event sourcing complement each other but neither requires the other.
  • What is a snapshot in event sourcing? → Every 100 events, save current state as a checkpoint. On startup, load latest snapshot + only events since that snapshot. Prevents replaying 10,000 events on every startup.

Caching — The single biggest performance win
5 strategies
C1–5
CachingRedis · Memcached🔥 Must Know
All 5 Cache Strategies — Cache-Aside · Write-Through · Write-Behind · Read-Through · Stampede Prevention
▼
Caching Analogy
Your brain is a cache. You don't call your mum to ask her birthday every time — you remember it. When you forget (cache miss), you call (go to DB). You remember again (populate cache). This is Cache-Aside.

Cache-Aside (Lazy Loading) — default strategy: Check cache → hit: return. Miss: load from DB, store in cache with TTL, return. Application controls caching. Most flexible.

Write-Through: Every write → cache AND DB simultaneously. Cache always fresh. Slower writes (2 writes). Good for: user profiles, settings where you need read-after-write consistency.

Write-Behind (Write-Back): Write → cache only → async flush to DB in batches. Fastest writes. Risk: lose data if cache crashes before flush. Good for: gaming scores, analytics counters, session data.

Read-Through: Cache loads from DB automatically on miss. App only talks to cache, never DB directly. Simpler app code. Cache must know DB schema — couples them.

Cache Stampede Prevention (Thundering Herd): Popular entry expires → thousands hit DB simultaneously. Fix: mutex lock (first req loads DB, others wait), probabilistic early expiry (randomly refresh 10% early), stale-while-revalidate (return stale instantly, refresh background).

Where to cache (from SD Primer): Client-side (browser cache, service worker), CDN (static assets at edge), Web server (Nginx microcaching), Application (Redis/Memcached), Database (query cache, buffer pool). Each layer reduces load on layers below.
Cache invalidation is the hard problem. When data changes, cached copies become stale. Strategies: TTL (expire after N seconds, simple but stale until expiry), Event-driven (invalidate on write, complex but accurate), Write-through (always consistent, slower writes).
Cross Questions — caching comes up in every design:
  • What is a cache hit ratio and what's acceptable? → hits / total requests. Aim for 90%+. Below 80% = cache isn't helping. Low hit ratio could mean: cache too small (increase memory), TTL too short, cached data rarely requested (reconsider what you cache).
  • How do you handle cache invalidation on write? → Simple: delete cache key on write (cache-aside with delete instead of update). On next read, DB hit repopulates. Write-through: update cache AND DB together. Event-driven: pub/sub message triggers invalidation across all nodes.
  • What is the stampede / thundering herd problem? → 1000 users check cached homepage. TTL expires. 1000 simultaneous requests all miss → 1000 DB queries at once → DB overload. Fix: mutex (one request loads, others wait for key to appear), probabilistic early expiry, or background refresh before TTL.
  • Redis vs Memcached — when to choose which? → Redis: supports complex data types (lists, sets, sorted sets for leaderboards, pub/sub, persistence, cluster mode). Memcached: simpler, faster for pure string key-value, multi-threading. Choose Redis for almost everything — it does more.

Communication Patterns
Patterns 12–18
12–18
Communication🔥 Frontend Relevant
REST · Message Queue · Pub/Sub · Event-Driven · Webhooks · SSE · WebSockets
▼
Communication Patterns Analogy
REST (Sync): Calling someone on the phone. You wait for them to answer and respond before you can do anything else.
Message Queue: Dropping a note in someone's mailbox. You walk away. They read it when they're ready.
Pub/Sub: Sending an email newsletter. Everyone subscribed gets a copy. You send once, everyone receives.
SSE: A TV broadcast. Server transmits, you receive. You can't reply.
WebSocket: A real-time phone call where both sides can talk simultaneously.

REST / Request-Response (Sync): Client sends request, waits for response. Simplest. Client blocked while waiting. Cascading failures if services are chained. HTTP + JSON.

Message Queue (Async, P13): Producer → Queue → Consumer. Producer doesn't wait. Decouples services. Durable (queue stores messages if consumer is down). BullMQ (Node.js + Redis), SQS (AWS), RabbitMQ. Each message goes to ONE consumer.

Pub/Sub (P14): Publisher → Topic → ALL subscribers. Unlike queue (one consumer), pub/sub delivers to everyone subscribed. "OrderCreated" → inventory, notifications, analytics all react. Kafka, Google Pub/Sub.

Event-Driven Architecture (P15): Services emit and react to events. No direct calls between services. OrderService emits "OrderPlaced". InventoryService reacts. PaymentService reacts. Loose coupling.

Webhooks (P16): Reverse HTTP. Server POSTs to your URL when event occurs. Stripe, GitHub, Twilio. Must handle delivery failures + idempotency (same event may arrive twice).

SSE / Server-Sent Events (P17): One-directional server→client over HTTP. Server pushes events as they happen. LLM token streaming (InterviewAI), live notifications, price tickers. Simpler than WebSockets.

WebSockets (P18): Full bidirectional persistent connection. Real-time chat, multiplayer games, collaborative editing. Higher infrastructure complexity at scale.

Asynchronism benefits (from SD Primer): Decouples slow operations from user-facing requests. User clicks "export CSV" → immediate response "we'll email it to you" → background worker generates CSV. User not blocked. Back pressure: if queue grows too fast, signal producers to slow down.
Cross Questions:
  • Queue vs Pub/Sub — exact difference? → Queue: one message consumed by exactly ONE consumer (competing consumers). Pub/Sub: one message delivered to ALL subscribers (fan-out). Use queue for distributing work across workers. Use pub/sub when multiple services need to react to the same event.
  • How did InterviewAI use SSE? → When interview scoring starts, SSE stream opens. Each scoring token streamed as it's generated by the LLM. Frontend renders typing effect. 1-second perceived response time vs 15-second wait for full response.
  • What is back pressure? → Consumer processes slower than producer produces. Queue fills up. Memory pressure. Crash. Solution: bounded queues (block or drop when full), adaptive rate limiting (slow producer when queue is deep), auto-scale consumers.
  • What is exactly-once delivery? → Guarantee a message is processed exactly once despite retries and failures. Very hard to achieve. Most systems offer at-least-once. Solution: make consumers idempotent — safe to process the same message twice (check if already processed before executing).

19–25
Reliability🔥 Critical for interviews
Circuit Breaker · Retry+Backoff · Bulkhead · Timeout · Idempotency · DLQ · Graceful Degradation
▼
Circuit Breaker Analogy
Your house has an electrical circuit breaker. If too many appliances draw power simultaneously, the breaker TRIPS (opens). This stops the overload from starting a fire. After a while, you reset it (half-open state — test if safe). If OK, it closes again. Failing services are the overloaded circuit.

Circuit Breaker (P19): 3 states — CLOSED (normal, requests pass), OPEN (too many failures, fail fast without calling the service), HALF-OPEN (test one request to see if service recovered). Prevents cascade failures. Hystrix, Resilience4j.

Retry with Exponential Backoff + Jitter (P20): Retry after 1s, 2s, 4s, 8s. Add random jitter (±500ms) to prevent all clients retrying at the same moment (thundering herd). Maximum 3-5 retries then fail.

Bulkhead (P21): Separate resource pools for different workloads. Named after ship compartments — if one floods, others stay intact. Tenant A gets 10 threads, Tenant B gets 10 threads. Tenant A misbehaving doesn't starve Tenant B.

Timeout (P22): Every external call gets a maximum time. Set = 2-3× P99 of healthy response time. Without timeouts: slow service → caller thread hangs forever → threads exhausted → system unresponsive. Timeout is the foundation. Add before everything else.

Idempotency (P23): Processing same request twice produces same result as once. Client sends UUID idempotency key. Server stores processed keys. Duplicate → return cached result. Payment charged once despite multiple retries. Booking created once.

Dead Letter Queue / DLQ (P24): Message fails after N retries → moved to DLQ instead of blocking main queue. Without DLQ: one bad message blocks all subsequent messages forever. With DLQ: bad message quarantined, main queue flows normally. Investigate DLQ separately.

Graceful Degradation (P25): Non-critical feature fails → serve degraded but functional experience. Recommendation service down → show trending instead of personalised. Image service slow → text-only. Design what "degraded mode" looks like BEFORE it happens.

Use these together: Timeout (catch slow calls) → Retry (handle transient failures) → Circuit Breaker (handle sustained failures). Stack these on every external service call.
Cross Questions:
  • What is a cascading failure and how do circuit breakers prevent it? → Service A calls B calls C. C fails → B waits for C until timeout → A waits for B → all three fail. Circuit breaker on B's call to C → when C starts failing, B immediately returns error instead of waiting → A gets fast error, can degrade gracefully instead of hanging.
  • How do you implement idempotency in a payment API? → Client generates UUID idempotency_key. POST /charge {amount, idempotency_key: "uuid-123"}. Server: INSERT INTO charges (..., idempotency_key) ON CONFLICT (idempotency_key) DO NOTHING RETURNING id. If duplicate: fetch existing charge and return it. Stripe uses this exact pattern.
  • How did thesqua.re encounter the real-world version of reliability patterns? → Retell AI webhook calls were blocked by Cloudflare WAF. Our Retell integration was failing. Solution: add Retell IPs to Cloudflare WAF allowlist. Lesson: infrastructure layers (CDN, WAF, proxies) can silently drop traffic — check network path before code when debugging.
  • Why is timeout the most important pattern? → Without timeouts, one slow downstream service can exhaust all your threads. Thread pool of 100 → 100 requests all hanging waiting for slow service → new requests queue → everything grinds to halt. Timeout is the first line of defence.

Scaling Patterns
Patterns 26–30 + Load Balancing deep dive
26–30
ScalingNginx · AWS ALB · GCP LB🔥 Always in SD questions
Horizontal Scaling · Vertical Scaling · Load Balancing · Auto-Scaling · Connection Pooling
▼
Scaling Analogy
Vertical: Replace your car with a bigger car. Faster, but there's a biggest car. Expensive.
Horizontal: Add more cars. Any number of cars. Requires coordination (load balancer = traffic controller who directs cars to lanes). Cars must not have "stuff in the boot" (stateful) or they can't be swapped out.

Horizontal Scaling (P26): Add more servers. Requires stateless servers (session in Redis, not local memory). Load balancer distributes requests. Scales indefinitely in theory. First choice for cloud-native apps.

Vertical Scaling (P27): Bigger server (more CPU, RAM). Simple — no architecture change. Has a ceiling. Single point of failure. Good for: databases (sharding complex, upgrade server simple), quick fix before horizontal.

Load Balancing (P28): Algorithms: Round Robin (equal turns), Least Connections (to least loaded server — best for variable request duration), Weighted Round Robin (powerful servers get more), IP Hash (sticky sessions — same client → same server). L4 (TCP, fast) vs L7 (HTTP, smart routing).

Auto-Scaling (P29): Add/remove instances automatically based on metrics. Trigger: CPU > 70% → add instance, < 30% → remove. Scale-up time: 2-5 minutes (containers faster than VMs). Metric choices: CPU (simple), QPS (better for APIs), queue depth (best for async workers). GCP Cloud Run scales to zero — no idle cost.

DB Connection Pooling (P30): Opening a DB connection = ~50ms TCP handshake + auth. Pool maintains 20-100 open connections. Requests borrow a connection, use it, return it. PgBouncer for PostgreSQL. Rule of thumb: pool_size = (core_count × 2) + effective_spindles.

Stateless design is the key: If server has state (in-memory session, local files), you can't add more servers because the next request might go to a different server that doesn't have the state. Solution: all state goes to shared stores (Redis for sessions, S3/GCS for files, DB for persistent data).
Cross Questions:
  • What makes a service stateless? → No local state. Sessions in Redis (not in-memory HashMap). Files in GCS/S3 (not local filesystem). Each request contains everything needed to process it (or is looked up from shared store). Any of the N servers can handle any request.
  • L4 vs L7 load balancing — practical difference? → L4: routes by IP/port. Faster (doesn't inspect content). Good for TCP/UDP traffic. L7: reads HTTP headers, URLs, cookies. Can route /api → API servers, /media → media servers. Enables A/B testing, canary deployments, content-based routing. Nginx acts as L7 LB.
  • How does Cloud Run auto-scaling work? → Each request creates/reuses a container. Traffic drops → scale to zero. No idle cost. Scale-up = ~100ms for warm containers. First request after scale-to-zero = cold start (~2s). Set min-instances=1 for latency-sensitive APIs to avoid cold start.

Data Processing Patterns
MapReduce · Stream · Lambda · CDC
31–34
Data ProcessingKafka · Flink · Debezium
MapReduce · Stream Processing · Lambda Architecture · Change Data Capture (CDC)
▼
MapReduce Analogy
You have 10,000 books to count word frequencies. Instead of reading all books yourself: give 100 books to each of 100 people (MAP — they each count words in their pile). Then collect all their counts and add them up (REDUCE). Parallel processing.

MapReduce (P31): Map phase: split large dataset, each machine processes its portion independently. Reduce phase: combine results. Foundation of Hadoop, Spark batch jobs. High latency (minutes-hours). Use for: daily analytics, ETL jobs, log aggregation.

Stream Processing (P32): Process data event-by-event as it arrives. Sub-second latency. Kafka Streams, Apache Flink, Spark Streaming. Use for: real-time fraud detection (flag suspicious transaction NOW not tomorrow), live dashboards, real-time recommendations.

Lambda Architecture (P33): Run batch AND stream in parallel. Batch = accurate but slow. Stream = fast but approximate. Serving layer merges both. Use when you need both real-time trends AND accurate daily aggregates. Downside: duplicate code for two pipelines.

Change Data Capture / CDC (P34): Capture DB changes in real-time from WAL. Debezium → Kafka → downstream consumers. Keep search index (Elasticsearch) and cache (Redis) in sync with DB without polling. Used at thesqua.re to sync Rentals United property data changes to availability search.

Kappa Architecture (simplification of Lambda): Use only stream processing. Replay historical data through stream processor for batch-level accuracy. Simpler (one pipeline vs two). Use when stream processing is fast enough for your accuracy needs.
Cross Questions:
  • Why did Lambda Architecture fall out of favour? → Maintaining two parallel pipelines (batch + stream) with the same logic in different frameworks is painful. Same bug must be fixed in two places. Kappa (stream-only) is simpler when stream processing can handle the load.
  • How does CDC help keep Elasticsearch in sync with PostgreSQL? → Debezium connects as a PostgreSQL logical replication client. Reads WAL in real-time. Each change → Kafka message. Elasticsearch consumer reads Kafka and indexes/updates/deletes. Lag typically < 1 second. No cron job polling needed.
  • What is backpressure in stream processing? → Consumer processes slower than producer publishes → buffer fills → memory pressure → crash. Solutions: bounded queues (block when full), consumer auto-scaling (add consumers when queue grows), producer rate limiting (slow down when queue is deep).

API Design Patterns
Gateway · BFF · Rate Limiting · Pagination · Versioning
35–39
API Design🔥 Architecture Level
API Gateway · Backend for Frontend · Rate Limiting · Cursor Pagination · API Versioning
▼
API Gateway Analogy
A shopping mall has one main entrance (security, bag check) instead of each shop having its own entrance. The gateway handles common concerns (auth, rate limiting) once instead of every shop (service) implementing it separately.

API Gateway (P35): Single entry point for all clients. Handles: JWT verification, rate limiting, routing (/api/v1/users → UserService), SSL termination, logging, request transformation. Kong, AWS API Gateway, Nginx. Clients call one URL not 20 service URLs.

BFF — Backend for Frontend (P36): Separate API layer per client. Mobile BFF: lightweight JSON, image URLs (not blobs), minimal fields. Web BFF: richer responses, more data. Internal BFF: full access. Use when mobile and web have significantly different data needs to avoid over-fetching.

Rate Limiting (P37): Limit requests per client/IP/API key per time window. Token Bucket (allows bursts — best for public APIs), Fixed Window (simple), Sliding Window (accurate, no boundary spike). Redis INCR + EXPIRE for distributed rate limiting across servers.

Cursor-Based Pagination (P38): Use opaque cursor pointing to last item instead of offset. GET /posts?after=cursor_abc&limit=20. Why better: offset pagination = scan 10,000 rows and discard first 9,980 (slow). Cursor = index lookup from exact position (fast). Also consistent when items are inserted/deleted mid-pagination.

API Versioning (P39): URL versioning (/api/v1/, /api/v2/) most common and transparent. Header versioning (Accept: application/vnd.api+json;version=2). Never break existing clients — maintain old version during migration window. Deprecation policy: 6 months minimum notice.

Cross Questions:
  • Token bucket vs sliding window rate limiting — when to use which? → Token bucket: allows bursts (100 req/10s = can do all 100 in 1 second then none for 9). Good for APIs where burst traffic is legitimate. Sliding window: exact 100 req in any 10-second window, no bursting. Good for strict fairness.
  • Why is cursor pagination better for infinite scroll? → Offset-based: page 500 = skip 9,980 rows (DB scans and discards). Slow. Also: if items are added to feed while scrolling, offset pagination skips or duplicates items. Cursor: anchored to specific item ID, always consistent, O(1) via index.
  • API Gateway vs Reverse Proxy — what's the difference? → Reverse proxy: SSL termination, routing, caching, compression. Simpler. Nginx. API Gateway: all of above + auth, rate limiting, API key management, analytics, request/response transformation, service discovery. Kong is an API Gateway built on Nginx.

Infrastructure Patterns
CDN · Reverse Proxy · Service Mesh · Sidecar
40–43
InfrastructureCloudflare · Nginx · K8s · Istio
CDN · Reverse Proxy · Service Mesh · Sidecar Pattern
▼
CDN Analogy
McDonald's doesn't ship every burger from one central kitchen to every customer worldwide. They have local restaurants (edge nodes) everywhere. Your meal is made near you. CDN = same idea for web content.

CDN — Content Delivery Network (P40): Edge servers worldwide cache static content. User in Mumbai gets served from Mumbai edge (5ms) not US origin (200ms). 40× faster. Push CDN: you push content to edges proactively. Pull CDN: edge fetches from origin on first request then caches. Pull CDN is easier to manage.

Reverse Proxy (P41): Sits between clients and servers. Handles: SSL termination (HTTPS → HTTP internally), compression, caching, routing, health check-based routing. Nginx, HAProxy, Cloudflare. Every production web service uses one.

Service Mesh (P42): For 50+ microservices. Sidecar proxy (Envoy) runs alongside each service in the same pod. Handles all service-to-service concerns: load balancing, retries, circuit breaking, mutual TLS (mTLS), distributed tracing. Application code never handles these — the sidecar does. Istio manages the mesh.

Sidecar Pattern (P43): A helper container runs alongside the main service container. Handles cross-cutting concerns: log shipping (tail app logs → send to Elasticsearch), config refresh (watch for changes → reload app), health reporting. App stays focused on business logic.

Service Mesh trade-off: Doubles the number of running containers. Every request passes through two proxy hops (sender sidecar + receiver sidecar). Adds ~1-5ms latency per call. Debugging is harder — network issues may appear in sidecar logs, not app logs. Only justified at large scale (50+ services).
Cross Questions:
  • Push CDN vs Pull CDN — when to choose? → Push: you control when content goes to edges. Good for large files that change infrequently (video, software downloads). Pull: edge fetches from origin on first miss, caches with TTL. Good for web assets (JS/CSS/images) that change regularly. Pull CDN is the default choice — simpler to manage.
  • What is cache-busting with CDN? → URL contains content hash: /app.a3b4c5d6.js. When file changes, hash changes, new URL → CDN has no cache for new URL → fresh fetch from origin. Old URL still cached (fine — nobody requests it after deploy). No manual cache invalidation needed.
  • Why did Cloudflare WAF cause issues at thesqua.re? → Cloudflare WAF blocked Retell AI's webhook POST requests because Retell's IP range triggered bot/DDoS protection rules. The fix was adding Retell's IP ranges to Cloudflare's WAF allowlist. Lesson: WAF rules need to whitelist known third-party service IPs.

Consistency + Security Patterns
2PC · Saga · Distributed Lock · Feature Flags · Tracing
44–50
Consistency🔥 Senior Level
2PC · Saga · Eventual Consistency · Distributed Locking · Zero Trust · Distributed Tracing · Feature Flags
▼
Saga vs 2PC Analogy
2PC (Two-Phase Commit): Everyone in a meeting must agree before anyone acts. One person offline = entire meeting blocked. Coordinator is the chairman — if he leaves mid-meeting, everyone freezes.

Saga: Each department acts independently. If department B fails, department A reverses its action (compensating transaction). No central coordinator needed.

Two-Phase Commit (P44): Coordinator: Phase 1 → "Can all of you commit?" Phase 2 → "OK all commit / all rollback." Atomic across services. Problem: if coordinator crashes between phases, everyone holds locks forever. Blocking, slow, doesn't scale to many participants. Use only for same-DB distributed transactions.

Saga Pattern (P45): Sequence of local transactions. Each service does its part and publishes event. If step N fails, steps N-1 to 1 execute compensating transactions (undo). No distributed locks. Works across microservices with different DBs. Orchestration (central coordinator calls each service) or Choreography (each service reacts to events).

Eventual Consistency (P46): System reaches consistent state eventually, given no new updates. Temporary inconsistency is acceptable. DNS propagation = eventually consistent. Social media likes counts = eventually consistent. Accept for: counters, feeds, recommendations. Reject for: payments, inventory, booking availability.

Distributed Locking (P47): Mutex across multiple servers. Redis SETNX with TTL: SET lock_key "1" NX EX 10. Prevents double-booking, duplicate job execution. Redlock algorithm (5 Redis nodes) for high reliability. Release lock after work done.

Zero Trust Security (P48): "Never trust, always verify." Even internal service-to-service calls are authenticated. mTLS (mutual TLS) — both parties verify each other's certificates. JWT between services. Least privilege — each service only accesses what it needs. Istio service mesh handles mTLS transparently.

Distributed Tracing (P49): Assign trace_id at entry point. Each service adds a span (start time, duration). Correlate all spans to see full request path. "Why is checkout slow?" → trace shows payment service took 4.8s. OpenTelemetry → Jaeger/Zipkin/Datadog. Essential for debugging microservices.

Feature Flags (P50): Toggle features at runtime without deploy. Canary release (10% → 50% → 100%), A/B testing, kill switch for broken features. Store in DB or LaunchDarkly. Instant rollback = flip flag. Built into InterviewAI admin panel.

Cross Questions:
  • Why does Saga solve what 2PC cannot? → 2PC holds distributed locks across all services during entire transaction. If any service is slow → everyone waits. Saga: each service makes local transaction, publishes event, moves on. No blocking. If step fails, compensating transactions undo previous steps asynchronously.
  • Saga orchestration vs choreography? → Orchestration: central coordinator calls each service in sequence. Easier to see the flow, harder single point. Choreography: each service reacts to events and emits next event. Decoupled, harder to debug. Choose orchestration for complex flows where visibility matters.
  • How does feature flagging enable safe deployments? → Deploy code behind a flag (disabled). Enable for 1% of users. Watch metrics. 10% → 25% → 50% → 100%. If something breaks: flip flag to off in 30 seconds. No rollback deployment needed. This is how Netflix, Facebook deploy without downtime.
  • What is a trace_id vs span_id? → trace_id: unique ID for the entire request journey across all services (stays same throughout). span_id: unique ID for work done by ONE service for that request. Multiple spans compose one trace. Parent-child span relationships show the call tree.

Q1
Classic🔥 Most Common
Design Pastebin / URL Shortener (Bit.ly / TinyURL)
▼

Step 1 — Clarify & Estimate:

  • 100M new URLs/day (write), 10B redirects/day (read) → 100:1 read:write ratio
  • URL active 5 years, 6-char short codes (62^6 = 56 billion possible codes)
  • Storage: 100M × 365 × 5 × 500 bytes = ~90 TB (need sharding)
  • QPS: 10B / 86400 = ~115K redirects/sec at peak

Step 2 — High Level Design: Client → Load Balancer → API Servers → Cache (Redis) → PostgreSQL (sharded). Separate read path (redirect) from write path (shorten).

Step 3 — Core Components:

  • Code generation: MD5(URL) → Base62 encode → take first 6 chars. Handle collisions: retry with salt (URL + current_timestamp). Or: use auto-increment ID → Base62 encode (guarantees unique). Pre-generate codes in batch → store in available_codes table.
  • Redirect: GET /{code} → check Redis cache → if miss, query DB → cache with 24h TTL → 301 (permanent, browser caches, less tracking) or 302 (temporary, each click tracked).
  • Storage: PostgreSQL table: (code, long_url, user_id, created_at, expires_at). Shard by code hash. Index on code for O(log n) lookups.

Step 4 — Scale: Redis caches hot URLs (80/20 rule — 20% of URLs get 80% traffic). 100GB Redis covers most traffic. Shard DB when single node insufficient. CDN for global redirect performance.

Cross Questions:
  • 301 vs 302 redirect? → 301 permanent: browser caches it, doesn't hit your server on repeat visits. Less analytics but lighter server load. 302 temporary: every click hits your server. Enables click analytics. Use 302 if analytics matter, 301 if you want to offload traffic.
  • How would you add analytics (click counts)? → Async: on each redirect, publish {code, timestamp, user_agent, IP} to Kafka. Analytics consumer aggregates in background. Don't block the redirect path for analytics.

Q2
Classic🔥 Twitter / Facebook
Design Twitter Timeline and Search (Social Feed)
▼

Estimates: 300M users, 600 tweets/sec write, 600K reads/sec (reads ≫ writes). 100 avg followers per user.

Two approaches for timeline generation:

Approach 1 — Fan-out on Write (push model):
User posts tweet → immediately write tweet ID to every follower's timeline cache (Redis sorted set). Reading timeline = one Redis lookup. Fast reads. Expensive writes (celebrity with 10M followers = 10M Redis writes per tweet). Good for non-celebrities.
Approach 2 — Fan-out on Read (pull model):
User posts tweet → store tweet. On timeline read: fetch IDs of people I follow → fetch their recent tweets → merge + rank. Slow reads (many DB queries). Cheap writes. Good for celebrities (Taylor Swift's 100M followers can't get 100M writes per tweet).

Hybrid approach (Twitter actual): Regular users → fan-out on write (Redis timeline cache). Celebrities → excluded from fan-out. On timeline read: merge pre-computed timeline (non-celebrities) + live fetch for followed celebrities. Best of both.

Search: Tweets indexed in Elasticsearch with Kibana. Full-text search on tweet content. Trending topics = count hashtag occurrences in sliding window via Redis sorted sets.

  • Why not fan-out on write for celebrities? → Justin Bieber has 300M followers. One tweet = 300M Redis writes. Even at microsecond per write, that's 300 seconds. Unacceptable. Hybrid model handles celebrity traffic by fetching their tweets live at read time.
  • How do you handle tweet ordering? → Snowflake IDs (Twitter's system): 64-bit = timestamp (41 bits) + datacenter (5 bits) + machine (5 bits) + sequence (12 bits). IDs are time-sortable, globally unique, no central coordinator. Sort by ID = sort by time.

Q3
Classic🔥 Nagarro Relevant
Design a System That Scales to Millions of Users on AWS/GCP
▼

This is the SD Primer's famous "scaling AWS" question. Shows progressive evolution.

Stage 1 — Single server (1-100 users): Everything on one server. DB + app + web server. Simple. Don't over-engineer.

Stage 2 — Separate web/app and DB (100-1K users): Different scaling needs: web server needs more CPU, DB needs more RAM. Vertical scale DB first.

Stage 3 — Load balancer + multiple app servers (1K-10K users): App servers stateless. Sessions in Redis. Load balancer. Now no single point of failure in app tier.

Stage 4 — DB replication (10K-100K users): Read replicas for DB (90% of queries are reads). Primary handles writes. CDN for static assets. Reduces DB load dramatically.

Stage 5 — Caching layer (100K-1M users): Redis/Memcached in front of DB. Cache most-read data. 90% cache hit rate → 90% fewer DB queries. DB can handle the remaining 10%.

Stage 6 — DB sharding + CDN (1M+ users): DB can't scale vertically anymore. Shard by user_id. CDN for all static + some dynamic content. Multiple datacenters for global users.

The progression of patterns: Single server → Separate concerns → Horizontal scaling → Replication → Caching → Sharding. Each stage introduces complexity only when needed. Don't shard before you need to.

Cross Questions:
  • How does thesqua.re map to this model? → Stage 4-5. Flask API on Cloud Run (horizontal scaling, auto-scale). PostgreSQL on Cloud SQL with read replicas for property search. Redis cache for frequent queries. Cloudflare CDN for static assets. Not at sharding scale yet.
  • When do you add caching vs when do you scale the DB? → Cache first: 90% read hit rate = 10× effective DB capacity with no hardware cost. Only scale DB hardware when you've maximised caching. Only shard when vertical scaling + caching is insufficient (typically 10M+ users, 100K+ writes/sec).
