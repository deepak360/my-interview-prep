PythonTricky
What is the GIL in CPython and how does it affect multithreading performance?
▼

The Global Interpreter Lock (GIL) is a mutex in CPython that allows only one thread to execute Python bytecode at a time. It protects CPython's reference-counted memory model from race conditions.

  • CPU-bound tasks: threads don't scale beyond one core — GIL serialises them
  • I/O-bound tasks: GIL is released during I/O waits, so threading helps for network/disk
  • Fix: use multiprocessing (separate processes, each with its own GIL)
import threading def cpu_task(): n = 0 for _ in range(10_000_000): n += 1 # GIL: threads compete — slower than sequential for CPU work t1 = threading.Thread(target=cpu_task) t2 = threading.Thread(target=cpu_task) t1.start(); t2.start(); t1.join(); t2.join() # Fix: multiprocessing — each process has its own GIL from multiprocessing import Pool with Pool(4) as p: p.map(cpu_task, [None] * 4) # true parallelism
Key insight: asyncio + threading → I/O concurrency (GIL released during waits). multiprocessing → CPU parallelism (bypasses GIL entirely). For ML inference use multiprocessing workers or a C-accelerated library like NumPy/PyTorch that releases the GIL internally.
Cross-question: "Design a CPU-bound ML inference service — would you use multiprocessing, asyncio, or Celery workers? What are the trade-offs, and how does FastAPI handle async vs sync endpoints internally?"

Strong answer: FastAPI runs sync endpoints in a threadpool, async endpoints on the event loop. For CPU-bound inference, a separate model server (Triton, TorchServe) or Celery + Redis queue isolates the GIL entirely.

▼

What are Python descriptors? How do @property and @classmethod use them internally?
▼

A descriptor is any object defining __get__, __set__, or __delete__. Python's attribute lookup triggers the descriptor protocol when accessing class attributes.

  • Data descriptor: both __get__ and __set__ (e.g. @property) — takes priority over instance __dict__
  • Non-data descriptor: only __get__ (functions, @classmethod) — instance dict can shadow it
class Validator: def __set_name__(self, owner, name): self.name = name def __get__(self, obj, objtype=None): if obj is None: return self return obj.__dict__.get(self.name) def __set__(self, obj, value): if not isinstance(value, int) or value < 0: raise ValueError(f"{self.name} must be non-negative int") obj.__dict__[self.name] = value class Order: quantity = Validator() price = Validator() o = Order() o.quantity = 5 # triggers __set__ o.quantity = -1 # raises ValueError

PythonTricky
What is the difference between __new__ and __init__? When would you override __new__?
▼

__new__ creates and returns the instance. __init__ receives the already-created instance and initialises it. Override __new__ to control instance creation itself: Singleton, cached instances, subclassing immutable types.

class Singleton: _instance = None def __new__(cls, *args, **kwargs): if cls._instance is None: cls._instance = super().__new__(cls) return cls._instance # always the same object def __init__(self, val): self.val = val # still re-runs every time! a = Singleton(1) b = Singleton(2) print(a is b) # True print(a.val) # 2 — __init__ ran again on same object
Gotcha: __init__ still runs even when __new__ returns the cached instance. Guard with if not hasattr(self, '_initialised') to initialise only once.

ReactTricky
What is the virtual DOM? How does it differ from the real DOM and what are its performance trade-offs?
▼

The vDOM is a lightweight in-memory JS object tree mirroring the real DOM. On state change, React renders a new vDOM tree, diffs it O(n), and batches minimal real DOM mutations. Real DOM mutations are expensive because they can trigger layout/paint cycles; the vDOM batches changes outside the pipeline.

Trade-off: vDOM overhead makes single-element updates slightly slower than targeted el.textContent = x. The benefit appears at scale with 100s of components. Svelte and Solid.js compile away the vDOM entirely — they produce direct DOM operations at build time with no runtime diffing overhead.

CSSTricky
Explain CSS specificity calculation and the cascade. How does !important interact?
▼

Specificity is a 3-tuple (A, B, C): A = inline styles, B = ID count, C = class/attribute/pseudo-class count. Element selectors score below C. Higher tuple wins regardless of source order; equal specificity → last declared wins. !important overrides all specificity.

/* (0,0,1) */ a { color: green; } /* (0,1,1) */ .nav a { color: blue; } /* (1,0,0) */ #header { color: red; } /* always beats above */ /* !important overrides all */ a { color: purple !important; } /* Two !important declarations → fall back to specificity */ /* #nav .item:hover span → (1, 2, 1) */
!important arms-race: two competing !important declarations fall back to specificity again. Overuse makes CSS unmaintainable. Prefer CSS Layers (@layer) for cascade control.
Cross-question: "How does :where() differ from :is() in specificity? How does @layer (CSS Cascade Layers) give a more maintainable alternative to !important for managing library vs application styles?"

PostgreSQLTricky
Explain MVCC in PostgreSQL — how does it enable concurrent reads and writes without locking?
▼

MVCC stores multiple versions of each row. PostgreSQL adds xmin (created by) and xmax (deleted by) system columns. Each transaction sees a snapshot consistent with its start time. Readers never block writers; writers never block readers.

-- Transaction A reads its consistent snapshot BEGIN; -- snapshot taken at T1 SELECT balance FROM accounts WHERE id = 1; -- returns 1000 -- B updates and commits concurrently (no lock on A's read) UPDATE accounts SET balance = 800 WHERE id = 1; COMMIT; -- A still sees 1000 — its snapshot is unchanged SELECT balance FROM accounts WHERE id = 1; -- still 1000 COMMIT; -- Dead tuples accumulate; check and clean them SELECT relname, n_dead_tup, last_vacuum FROM pg_stat_user_tables;
Pitfall: long-running transactions prevent VACUUM from reclaiming old row versions → table bloat. Monitor pg_stat_activity for idle-in-transaction connections.

▼

  • 2NF: no partial dependency on a composite key
  • 3NF: no transitive dependency — non-key attrs depend only on the key

GitTricky
Explain Git's internal object model: blobs, trees, commits, and refs.
▼

Git is a content-addressed filesystem. Every object is stored by SHA-1 hash in .git/objects/:

  • blob: raw file contents (no filename or metadata)
  • tree: directory listing — maps filenames to blob/tree SHAs
  • commit: tree SHA + parent SHA(s) + author + timestamp + message
  • ref: named pointer to a commit SHA (a branch is just a text file in .git/refs/)
git cat-file -t HEAD # 'commit' git cat-file -p HEAD # tree SHA, parent, author, message git cat-file -p HEAD^{tree} # directory listing (filename → SHA) git cat-file -p <blob-sha> # raw file content echo -n "hello" | git hash-object --stdin # hash any content cat .git/refs/heads/main # just a commit SHA cat .git/HEAD # ref: refs/heads/main

What is the CAP theorem? How do DynamoDB and PostgreSQL RDS make different trade-offs?
▼

CAP: a distributed system can guarantee at most two of Consistency (all nodes see same data), Availability (every request gets a response), Partition Tolerance (survives network splits). Since partitions are unavoidable, systems choose CP or AP.

SystemChoiceTrade-off
DynamoDB (default)APEventually consistent — may return stale data
DynamoDB (ConsistentRead: true)CP2× read cost, may block during partition
PostgreSQL RDS (primary)CPUnavailable ~30s during failover
PostgreSQL read replicaAPReplication lag — stale reads possible

Explain pod scheduling, resource requests vs limits, and what happens when limits are exceeded.
▼

Requests = guaranteed by scheduler (node must have capacity). Limits = maximum allowed. CPU over limit → throttled (not killed). Memory over limit → OOM killed → pod restarts. requests == limits = Guaranteed QoS class.

AWS
How does AWS Lambda's execution model work? Explain cold starts, concurrency, provisioned concurrency.
▼

Lambda runs in Firecracker micro-VMs. First invocation = cold start (100ms–2s: download code, init runtime, run module-level code). Subsequent invocations reuse the warm container. Concurrency = simultaneous invocations (default account limit: 1000). Provisioned concurrency pre-warms N containers — eliminates cold start at extra cost.

import boto3, json # Module-level code runs once on cold start — cache expensive init here dynamodb = boto3.resource('dynamodb') table = dynamodb.Table('Bookings') # reused across warm invocations def handler(event, context): # Runs on every invocation booking_id = event['pathParameters']['id'] item = table.get_item(Key={'id': booking_id}).get('Item') return {'statusCode': 200, 'body': json.dumps(item)}
